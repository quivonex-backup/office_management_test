================================================================================
PAYROLL APP — API REFERENCE FOR FRONTEND
================================================================================

Base URL       : /payroll/
Method         : All endpoints are POST
Auth           : Bearer token (IsAuthenticated)
Envelope       : { "status": true|false, "message": "...", "data": {...}?, "errors": {...}? }

Organization context:
  - If the logged-in user belongs to exactly one active organization,
    no organization_id is needed.
  - If the user belongs to multiple organizations, every request must
    include "organization_id" in the body.


================================================================================
BOOTSTRAP ORDER — READ THIS FIRST
================================================================================
Before any payroll run can succeed, data must exist in this order. Each step
depends on the one above it. If you call an endpoint before its prerequisites
exist, you'll get a 400 with a clear error message.

  STEP 0 (super admin — one time for the platform)
    └─ 1. Statutory rate configs    (federal defaults: PF, ESI, EPS, EDLI, LWF)
    └─ 2. Statutory slabs           (per-state PT slabs; optional if no PT)
    ** Without these, any org that enables PF/ESI/PT will fail generation.
    ** If no org uses statutory, you can skip these entirely.

  STEP 1 (org admin — one time per organization)
    └─ 3. Payroll settings           (cycle_start_day, salary_basis, payslip_mode)
    └─ 4. Company statutory settings (which schemes this org uses)
    └─ 5. Salary components          (Basic, HRA, PF, PT, etc.)
    └─ 6. Salary structures          (named templates — Junior Dev, Manager)
    └─ 7. Employee salary assignments (employee → structure, effective-dated)

  STEP 2 (org admin — monthly cycle)
    └─ 8. Preview payroll            (dry run, no save)
    └─ 9. Create payroll run         (DRAFT)
    └─ 10. Generate payroll          (creates PayrollRecords)
    └─ 11. Review records / manual adjustments if needed
    └─ 12. Finalize payroll          (locks the run)

  STEP 3 (org admin — after finalize)
    └─ 13. Record payment(s)         (single or bulk)
    └─ 14. View payment history

  EMPLOYEE (anytime after finalize)
    └─ View own payslips and salary assignment


CAN I TEST ADMIN APIS WITHOUT SUPER ADMIN SETUP?

  - YES, if your org will not use PF / ESI / PT / LWF.
    Set "payslip_mode": "SIMPLE" in payroll settings and skip the
    super-admin statutory setup entirely.

  - NO, if your org enables any statutory scheme in company statutory
    settings. You MUST create the relevant StatutoryRateConfig rows
    (and StatutorySlab rows for PT) before the first generate call.
    Missing rate config → ERROR record per employee with message
    "X is enabled for this organization but no rate is configured..."


================================================================================
SECTION 1 — SUPER ADMIN: STATUTORY RATE CONFIGS
================================================================================
Only super admins (user.is_superuser=true) can call these. Non-super-admins
receive 403. Creates FEDERAL defaults (organization=null) or per-org overrides.

--------------------------------------------------------------------------------
1.1  POST /payroll/statutory-rate-configs/list/
--------------------------------------------------------------------------------
Purpose : List all statutory rate configs
Request :
{
  "component_code": "PF_EMPLOYEE",   // optional: filter by code
  "organization_id": 5,               // optional: filter by org
  "include_federal": true             // optional, default true
}
Response 200:
{
  "status": true,
  "message": "Statutory rate configs fetched.",
  "data": [
    {
      "id": 1,
      "organization": null,
      "component_code": "PF_EMPLOYEE",
      "rate_percentage": "12.0000",
      "wage_ceiling": "15000.00",
      "calculation_base": "PF_ELIGIBLE",
      "effective_from": "2014-09-01",
      "effective_to": null,
      "notification_reference": "S.O. 1234(E)",
      "notes": "Statutory PF employee rate",
      "created_by": 1,
      "updated_by": 1,
      "created_at": "2026-01-01T00:00:00Z",
      "updated_at": "2026-01-01T00:00:00Z"
    }
  ]
}

--------------------------------------------------------------------------------
1.2  POST /payroll/statutory-rate-configs/create/
--------------------------------------------------------------------------------
Purpose : Create a federal or org-specific rate
Request :
{
  "organization": null,                // null = federal; N = org override
  "component_code": "PF_EMPLOYEE",     // PF_EMPLOYEE | PF_EMPLOYER | EPS | EDLI |
                                       // ESI_EMPLOYEE | ESI_EMPLOYER | PT | TDS |
                                       // LWF_EMPLOYEE | LWF_EMPLOYER
  "rate_percentage": "12.0000",
  "wage_ceiling": "15000.00",          // nullable: null = no ceiling
  "calculation_base": "PF_ELIGIBLE",   // BASIC | BASIC_DA | PF_ELIGIBLE |
                                       // ESI_ELIGIBLE | GROSS
  "effective_from": "2014-09-01",
  "effective_to": null,                // null = currently active
  "notification_reference": "S.O. 1234(E)",
  "notes": "..."
}
Response 201:
{
  "status": true,
  "message": "Statutory rate config created.",
  "data": { ...same shape as list item... }
}

--------------------------------------------------------------------------------
1.3  POST /payroll/statutory-rate-configs/update/
--------------------------------------------------------------------------------
Purpose : Update an existing rate config (partial)
Request :
{ "id": 1, "rate_percentage": "12.5000" }
Response 200:

  "data": { ...updated config... }
}

================================================================================
KEY NOTES FOR FRONTEND TEAM
================================================================================

1. PAYSLIP_MODES
   - "FULL":   Individual component breakdown + statutory line items
   - "SIMPLE": One GROSS earning line + LOP + NET. No statutory lines.
   - Both modes use the same PayrollRun / PayrollRecord / Payment workflow.

2. MISSING_ATTENDANCE_ACTION (per-org setting, default: "ABSENT")
   - "ABSENT" (default): Missing day treated as absent — deducted
   - "REVIEW":           Missing day held for review — NOT deducted,
                         sets requires_review=True on the record.
                         Finalize is BLOCKED until resolved
                         (via recompute or review_notes acknowledgment).
   - "SKIP":             Missing day skipped entirely — NOT deducted

3. SALARY_BASIS (per-org setting)
   - "CALENDAR_DAYS": per_day = monthly / actual calendar days in period
   - "FIXED_30":      per_day = monthly / 30
   - "WORKING_DAYS":  per_day = monthly / scheduled working days in period
                      (paid holidays and weekly offs NOT in denominator)

4. PAYMENT STATUS LIFECYCLE
   UNPAID → PARTIALLY_PAID → PAID
   Auto-computed from sum of PayrollPayment rows. Cannot be set manually.

5. GENERATION STATUS ON RECORDS
   - "GENERATED": Record created with computed payslip
   - "SKIPPED":   Employee has no salary assignment for this period
   - "ERROR":     Calculation failed (missing UAN, no rate, no PT slab, etc.)

6. PAYROLL RUN STATUS LIFECYCLE
   DRAFT → GENERATED → FINALIZED
   - Only FINALIZED runs are eligible for payment
   - Only DRAFT runs can be generated
   - Only GENERATED runs can be finalized

7. STATUTORY: WHAT'S AUTO-COMPUTED vs MANUAL
   AUTO (when enabled in company statutory settings):
     - PF employee, PF employer, EPS, EDLI
     - ESI employee, ESI employer
     - PT (from state slabs)
     - LWF employee, LWF employer
   MANUAL:
     - TDS: use POST /payroll/records/update-deductions/ per employee
     - PF admin charges: handled by CA in PF ECR filing (not in this system)

8. ORG SCOPING
   - Single-org users: omit organization_id
   - Multi-org users: MUST include organization_id in every request body

9. SUPER ADMIN GATE
   - All 6 super-admin endpoints require user.is_superuser=true
   - Non-super-admins get 403 even if they have an org membership

10. ENVELOPE
    All responses: { "status": true|false, "message": "...", "data": {...}? }
    Validation errors additionally include "errors": { "field": ["msg"] }
    The frontend should always check "status" before using "data".

11. UPI PAYMENT HELPERS
    Every payroll record in responses now includes:
      - "remaining": string decimal, always present, = net - paid_amount
      - "upi_link":  string or null, a pre-filled UPI deep link:
                     upi://pay?pa=<employee_upi>&pn=<name>&am=<remaining>&cu=INR&tn=<Month Year salary>

    Behavior:
      - employee.upi_id not set           → upi_link = null
      - payment_status == "PAID"          → upi_link = null
      - payment_status == "UNPAID"        → upi_link targets full net
      - payment_status == "PARTIALLY_PAID"→ upi_link targets remaining only

    Frontend rule:
      if (record.upi_link === null) hide the UPI / QR button
      else render QR from record.upi_link and/or "Open UPI App" button

    This is a CONVENIENCE only. No automated transfer. Admin still:
      1. Opens UPI app from the link
      2. Manually completes the transfer
      3. Returns and calls POST /payroll/payments/record/ with the UTR
         as "transaction_reference" and "payment_mode": "UPI"

    For bulk salary runs (many employees), use /payroll/payments/bulk-record/
    with a real bank batch reference — UPI link is for individual /
    one-off / small-org payments.
