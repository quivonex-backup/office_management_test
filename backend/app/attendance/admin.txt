================================================================================
ATTENDANCE APP — ADMIN / ORG OWNER API REFERENCE
================================================================================

Base URL   : /
Method     : All endpoints are POST
Auth       : Bearer token (IsAuthenticated)
Envelope   : { "status": true|false, "message": "...", "data": {...}?, "errors": {...}? }

Organization context:
  - Single-org users: omit organization_id
  - Multi-org users: include organization_id in body

Who uses this document:
  - Org owner / Admin
  - HR / attendance managers
  - Anyone configuring shifts, viewing org-wide attendance, reviewing corrections

NOTE: Employees DO NOT use the endpoints in this document — they have their
      own set (see the Employee document). A few endpoints appear in both
      because they work for both audiences (e.g. /detail/ scoped by role).

BOOTSTRAP ORDER:
  1. Attendance settings           → /attendance/settings/    (one-time)
  2. Shifts                        → /attendance/shifts/...   (one-time)
  3. Shift assignments             → /attendance/shift-assignments/...
  4. Weekly-offs and holidays      → /calendar/...            (separate app)
  5. Employee check-ins start flowing in
  6. Review corrections            → /attendance/corrections/review/
  7. Bulk mark absent if needed    → /attendance/bulk-mark-absent/

3.3  POST /attendance/shift-assignments/update/
--------------------------------------------------------------------------------
Request (partial):
{
  "assignment_id": 7,

  "effective_from": "2026-10-25",
  "effective_to": null
}
Response 200: { full assignment object }

--------------------------------------------------------------------------------
3.4  POST /attendance/shift-assignments/bulk-assign/
--------------------------------------------------------------------------------
Purpose : Assign ONE shift to MANY employees at once (all-or-nothing)
Request :
{
  "employee_ids": [12, 15, 18],
  "shift_id": 3,
  "effective_from": "2026-11-01",
  "effective_to": "2026-11-30"
}
Response 201:
{
  "status": true,
  "message": "Shift assigned to employees successfully.",
  "data": [ {assignment1}, {assignment2}, {assignment3} ]
}

Behavior:
  - Validates every employee before creating any row.
  - If ANY employee fails (wrong org, inactive, overlap) → 400 and nothing created.

--------------------------------------------------------------------------------
3.5  POST /attendance/shift-assignments/bulk-assign-pattern/
--------------------------------------------------------------------------------
Purpose : Assign a rotating shift pattern to many employees
Request :
{
  "employee_ids": [12, 15],
  "start_date": "2026-11-02",
  "pattern": [
    { "shift_id": 3, "duration_days": 7 },
    { "shift_id": 4, "duration_days": 7 }
  ],
  "repetitions": 2,
  "auto_close_prior": true
}
Response 201: { list of all created assignments }

How the pattern works:
  Day shift: Nov 2–8
  Night shift: Nov 9–15
  Day shift: Nov 16–22
  Night shift: Nov 23–29
  (4 assignment blocks per employee when repetitions=2)

Validations:
  - duration_days must be positive integer (booleans rejected).
  - All pattern shifts must be active in org.
  - All pattern shifts must share compatible weekly-off schedules
    (checked day-by-day via Calendar app — this is a hard requirement).
  - auto_close_prior=true will close prior OPEN-ENDED assignments
    (with safety check: rejects if attendance records exist on/after start_date
    for the previous shift).

--------------------------------------------------------------------------------
3.6  POST /attendance/shift-assignments/bulk-close/
--------------------------------------------------------------------------------
Purpose : Set effective_to on multiple existing assignments
Request :
{
  "assignment_ids": [101, 102, 103],
  "effective_to": "2026-10-31"
}
Response 200: { closed assignment objects }

Behavior:
  - Each assignment's effective_to must be >= its effective_from.
  - Closing must not overlap another assignment for the same employee.
  - Rejects if attendance records exist AFTER the new effective_to
    for that employee + shift combination.
  - Preserves history — nothing is deleted.

{
  "from_date": "2026-10-01",
  "to_date": "2026-10-31",
  "employee_ids": [12, 15]       // optional: restrict to specific employees
}

{
  "status": true,
  "message": "Bulk absent mark completed: 45 created, 120 already existed, 60 non-working days.",
  "data": {
    "created_count": 45,
    "skipped_existing": 120,
    "skipped_non_working": 60,
    "employees_processed": 10,
    "from_date": "2026-10-01",
    "to_date": "2026-10-31"

  - Skips non-working days (HOLIDAY/WEEKLY_OFF/NO_SHIFT_ASSIGNED).
  - Skips days where an AttendanceRecord already exists.
  - Never overwrites an existing record.

5.2  POST /attendance/corrections/review/
--------------------------------------------------------------------------------

{
  "correction_id": 1,
  "approve": true,
  "review_note": "Verified with gate log."
}
Request (reject):
{
  "correction_id": 1,
  "approve": false,
  "review_note": "Wrong date; please resubmit."

  - Approve must be a boolean: true or false.

================================================================================
KEY NOTES FOR FRONTEND — ADMIN SIDE
================================================================================

1. SETTINGS DRIVE EMPLOYEE UX
   If photo_required=true, the employee's app must enforce selfie capture.
   If location_required=true, the app must enforce GPS. Failing to do this
   means every employee punch returns 400. Read settings first and configure
   the employee screens accordingly.

2. SHIFT OVERLAP PREVENTION
   Assignments for the same employee cannot overlap in effective date range.
   If you're re-assigning an employee to a new shift mid-month, first
   update the OLD assignment's effective_to (or use bulk-close), THEN create
   the new one. Doing it in reverse will fail with "employee already has
   overlapping assignment".

3. BULK-ASSIGN IS ALL-OR-NOTHING
   If you send 100 employees and one fails, zero assignments are created.
   Surface the error message clearly to the admin.

4. ROTATING PATTERNS ARE HEAVILY VALIDATED
   Two shifts can only be rotated if their weekly-offs fall on the same
   days for the entire rotation period. A "General Shift (Sun off)" and a
   "Night Shift (Sat off)" cannot rotate — the API will reject the whole
   batch with "schedules differ on YYYY-MM-DD".

5. AUTO-ABSENT IS A TWO-STEP FEATURE
   - Turn it ON in settings (auto_mark_absent=true)
   - Then call bulk-mark-absent periodically (cron / scheduler / daily admin
     action). The setting alone does not auto-create records.

6. CORRECTIONS APPROVAL UPDATES ATTENDANCE IN PLACE
   When you approve a CHECK_IN or CHECK_OUT correction, the system:
   - Applies the new value
   - Recomputes net_work_minutes, late_minutes, early_departure_minutes,
     overtime_minutes, and status
   So one approved correction can flip PRESENT → HALF_DAY, or INCOMPLETE
   → PRESENT. Don't be surprised by the attendance row changing.

7. ATTENDANCE DETAIL IS ROLE-AWARE
   The same endpoint is used by admin (view any) and employee (view own).
   The backend blocks employees from viewing other employees' records.

SECTION — ACCESS + SCOPE (batch 2)
================================================================================

Permission codes come from the caller's access role (accounts/admin.txt,
ORGANIZATION STRUCTURE + ACCESS). The organization owner has every code.
Missing code -> 403 {"status": false, "message": "You do not have permission to perform this action."}

SCOPE (list endpoints marked "scope" below)
  Request : optional "scope": "self" | "team" | "all"
  Default : the widest scope the caller has.
  Clamp   : asking for more than allowed gives the next lower allowed scope
            (never an error, never more than asked). Invalid value -> 400
            "scope must be self, team or all."
  Team    : the caller + everyone below them through reports_to (all levels).
  Response: same body as before + top-level "scope_applied": "self"|"team"|"all"
  Show a Mine / My team / Everyone switch with only the allowed options:
  derive them from my-profile data.permissions.

--------------------------------------------------------------------------------
Endpoints
--------------------------------------------------------------------------------
  settings/                                settings.manage
  shifts/list/, shift-assignments/list/    settings.manage | attendance.view_all | attendance.view_team | attendance.correct
  shifts/create|update|deactivate/         settings.manage
  shift-assignments/create|update|bulk-*/  settings.manage
  list/                                    scope (attendance.view_self / view_team / view_all)
  detail/                                  own record, or a record inside the caller's scope (else 403)
  corrections/list/                        scope (same codes)
  corrections/create/                      own record; attendance.correct may file for others
  corrections/review/                      attendance.approve_correction + record in scope + not own
  bulk-mark-absent/                        attendance.correct

Review errors (403):
  "You cannot review your own request."
  "This record is outside your team."

Punch geofence (branch): the employee's branch latitude/longitude and
radius are used when the branch has coordinates (radius empty = settings
radius); otherwise the organization location. Each punch stores
verification_details.branch {id, name} | null and allowed_radius_meters.

Remote employees (employee.attendance_location_exempt = true): the location
check is skipped (no radius, no GPS accuracy check, GPS optional). Latitude /
longitude are still saved when sent and distance_meters is recorded.
verification_details.location_exempt = true on those punches. Photo / face and
shift rules are unchanged. Set the flag with employees/update/.

================================================================================
SECTION — ATTENDANCE KIOSK DEVICES (batch 12)   perm: attendance.device_manage
================================================================================
A kiosk is a shared tablet at the office entrance. It has its own login
(device code + password), separate from users. Employees punch on it with
their employee code (typed, or a QR that holds the code) + face.

POST /attendance/device/create/
  { "name": "Lobby tablet", "branch_id"?: 3, "device_code"?: "LOBBY-1", "notes"?: "..." }
  device_code optional: blank = auto "KSK-XXXXXX". Letters, digits, - and _ ,
  3-50 characters, unique, stored upper-case. Password is always generated
  (e.g. "k8Rm-42Tx-9pQa"). branch_id = an active branch of the organization
  (label only; the punch location is checked against the EMPLOYEE's branch).
  201 -> device object

POST /attendance/device/list/
  { "search"?: "lobby", "branch_id"?: 3, "include_inactive"?: false }
  200 -> [device, ...]   (passwords are shown)

POST /attendance/device/update/
  { "device_id": 1, "name"?, "branch_id"? (null clears), "notes"?, "device_code"?,
    "is_active"?: true (reactivate) }
  Changing device_code logs the tablet out.

POST /attendance/device/reset-password/   { "device_id": 1 }
  New password, tablet logged out, lock cleared. 200 -> device object

POST /attendance/device/deactivate/       { "device_id": 1 }
  Tablet logged out, login refused (403) until reactivated.

Device object:
{ "id": 1, "name": "Lobby tablet", "device_code": "KSK-7QX2LM",
  "password": "k8Rm-42Tx-9pQa", "branch": {"id": 3, "name": "Mumbai HQ"} | null,
  "notes": null, "is_active": true, "logged_in": true,
  "token_issued_at": "...", "locked_until": null, "last_login_at": "...",
  "last_seen_at": "...", "last_ip": "192.168.1.20", "created_at": "...", "updated_at": "..." }

Errors: 400 validation (device_code taken / invalid, branch not found),
403 without the permission, 404 device not in this organization.

SECTION — KIOSK APIs (batch 12)  — no user token
================================================================================
1) POST /attendance/kiosk/login/
   { "device_code": "KSK-7QX2LM", "password": "k8Rm-42Tx-9pQa" }   (code case-insensitive)
   200 { "token": "dvc_...", "device": {id, name, device_code, branch},
         "organization": {id, name, logo} }
   400 "Invalid device code or password."
   403 "Device is inactive."
   423 "Too many attempts. Try again in N minutes."  (5 wrong passwords -> 15 min lock)
   One session per device: a new login ends the previous token. The token does
   not expire; it ends on re-login, reset-password, code change or deactivate.
   Only a SHA-256 fingerprint of the token is stored (attendance_devices.token_hash).

2) POST /attendance/kiosk/punch/      header  Authorization: Device <token>
   multipart: punch_type (CHECK_IN | CHECK_OUT), employee_code,
              selfie (required when settings photo_required),
              latitude, longitude (required when settings location_required),
              gps_accuracy_meters?
   Same rules as the mobile punch (attendance/punch/): face match, branch
   geofence or remote exemption, shift, late, half day, overnight.
   The button must match the state:
     400 "No open check-in to check out from. Check in first."
     400 "Already checked in. Use check-out."
   201 { "employee": {id, employee_code, name, photo},
         "punch": {...same as mobile}, "attendance": {...same as mobile} }
   401 "Device not logged in." / "Device session ended. Log in again." / "Device is inactive."
   404 "Employee not found."   (only active employees of the device's organization)
   400 other punch errors (selfie required, face mismatch, outside location...)

   Stored like a mobile punch; verification_details also gets
   source "KIOSK", device_id, device_name, device_code. recorded_by is null.
   The employee sees it in my-attendance like any other punch.
   No logout API: the app just forgets the token.

SECTION — MISSED DAY REQUEST / WITHDRAW (batch 14)
================================================================================

POST /attendance/corrections/missed-day/        (#E; employee_id for others: attendance.correct)
  { "work_date": "2026-11-20",
    "check_in": "2026-11-20T09:05:00",       // ISO datetime, on work_date
    "check_out": "2026-11-20T18:10:00",      // after check_in, at most next day, not future
    "reason": "Forgot phone",
    "employee_id"?: 25 }
  For a day with NO check-in and NO check-out (no record, or an ABSENT /
  empty record). Creates the record if missing (INCOMPLETE) and two PENDING
  corrections: CHECK_IN + CHECK_OUT. Approvers are notified
  (ATTENDANCE_CORRECTION_SUBMITTED).
  201 { "attendance_id": 900, "work_date": "2026-11-20", "corrections": [ {..CHECK_IN..}, {..CHECK_OUT..} ] }
  400 missing fields (errors per field), future day, before joining date,
      times invalid, "Attendance already has a check-in or check-out for this
      day. Use corrections/create/ to change it.", "A correction request for
      this day is already pending."
  403 for someone else without attendance.correct.

POST /attendance/corrections/review/   (unchanged request)
  A missed-day pair is reviewed together: approving or rejecting either line
  does the same to the other (check-in applied first, then the day is
  recalculated: PRESENT / HALF_DAY / late...). Rejected pair -> day ABSENT.
  Response adds "paired_correction_id" only for a missed-day pair.

POST /attendance/corrections/cancel/            (#E; only the requester)
  { "correction_id": 77 }
  Withdraws a PENDING request (deleted; kept in the activity log). A
  missed-day pair is withdrawn together, and its empty record (created only
  for the request) is removed.
  200 { "withdrawn_correction_ids": [77, 78], "attendance_record_removed": true }
  400 "Only pending corrections can be withdrawn."  403 not your request.  404 not found.
