================================================================================
EXPENSES APP — ADMIN API REFERENCE
================================================================================

Base URL   : /
Method     : All endpoints are POST
Auth       : Bearer token (IsAuthenticated)
Envelope   : { "status": true|false, "message": "...", "data": {...}?, "errors": {...}? }

Organization context:
  - Single-org users: omit organization_id
  - Multi-org users: include organization_id in body

Who uses this document:
  - Super admin
  - Organization owner (Admin role)

"Admin" in this document means:
  - Super admin (is_superuser = true), OR
  - The organization's owner (organization.owner == current user)

1.1  POST /expenses/create/
--------------------------------------------------------------------------------
Purpose : Record a company expense (paid to vendor / for project)
Access  : Admin only
Content-Type : multipart/form-data

Request fields:
  title                string, required
  description          string, optional
  expense_type         enum (see EXPENSE TYPE), required
  amount               decimal, required, > 0
  expense_date         date (YYYY-MM-DD), required
  due_date             date, optional (must be >= expense_date)
  vendor               integer, optional (must belong to caller's org)
  project              integer, optional (must belong to caller's org)
  payment_status       enum: paid | unpaid (default unpaid)
  payment_date         date — required if paid, must be null if unpaid
  payment_method       enum — required if paid, must be null if unpaid
  reference_number     string — only for paid (must be null if unpaid)
  notes                string, optional
  documents            file(s), optional

Request example (FormData):
  title             = "Google Cloud invoice Oct"
  description       = "GCP invoice for October"
  expense_type      = "cloud"
  amount            = "12450.00"
  expense_date      = "2026-11-01"
  payment_status    = "paid"
  payment_date      = "2026-11-05"
  payment_method    = "bank_transfer"
  reference_number  = "NEFT-20261105-001"
  vendor            = 8
  project           = 12
  documents         = <gcp-invoice.pdf>

--------------------------------------------------------------------------------
Content-Type : multipart/form-data

Request fields:
  recurring_expense     integer, required
  year                  integer (2000-2100), required
  month                 integer (1-12), required
  amount                decimal > 0, required
  due_date              date, optional

  payment_date          required if paid
  payment_method        required if paid
  reference_number      only for paid
  notes                 string, optional
  documents             file(s), optional

Unique rule:
  One entry per (recurring_expense, year, month). Duplicate → 400.

Response 201: { full RecurringExpenseEntryDetailSerializer }

{
  "status": false,
  "message": "An entry already exists for this recurring expense and month."
}


--------------------------------------------------------------------------------
3.2  POST /expenses/recurring/entries/update/
--------------------------------------------------------------------------------
Content-Type : multipart/form-data
Request : entry_id (required) + any subset of the create fields + 
          remove_document_ids (optional, repeated) + documents (optional, repeated)
Response 200: { full entry detail }
Response 400 (validation):
Same validations as /recurring/entries/create/:
  - year in 2000-2100
  - month in 1-12
  - amount > 0
  - if payment_status=paid: payment_date and payment_method required
  - if payment_status=unpaid: payment_date, payment_method, reference_number must be null
Response 400 (unique clash on year/month change):
{
  "status": false,
  "message": "An entry already exists for this recurring expense and month."
}

================================================================================
KEY NOTES FOR FRONTEND — ADMIN SIDE
================================================================================

1. EXPENSE vs RECURRING EXPENSE — DIFFERENT ENUMS.
   Expense.expense_type has 13 values (food, travel, ..., professional_services, other).
   RecurringExpense.expense_type has 7 values (electricity, rent, cloud,
   internet, software, telephone, other). Use the right enum in each UI dropdown.

2. PAID/UNPAID CONSISTENCY.
   paid   → payment_date + payment_method required, reference_number optional
   unpaid → payment_date, payment_method, reference_number must all be null
   Validation rejects any mismatch.

3. RECURRING ENTRY UNIQUENESS.
   One entry per (recurring_expense, month, year). Duplicates → 400 with
   clear message. Admin must delete the existing entry or change month/year.

4. RECURRING ENTRY DEACTIVATE IS HARD DELETE.
   Unlike Expense and RecurringExpense (soft delete), the entry deactivate
   endpoint hard-deletes the row and removes all attached documents from S3.
   The audit log preserves the deletion record.

5. REIMBURSEMENT FLOW IS TWO-STEP.
   PENDING → APPROVED → PAID
           → REJECTED (terminal)
           → CANCELLED (terminal, employee-initiated)

   Admin duties:
   - review/       → move PENDING to APPROVED or REJECTED
   - mark-paid/    → move APPROVED to PAID

6. UPI LINK APPEARS ONLY ON APPROVED.
   The `upi_link` field is:
     null    → status is PENDING, REJECTED, CANCELLED, or PAID
     "upi://" → status is APPROVED AND employee has a UPI

   Frontend uses `upi_link` to render the QR code / "Open UPI App" button.
   Present it only while status is APPROVED.

7. REVIEW ENFORCES REJECTION REASON.
   Rejecting without `rejection_reason` → 400. The employee sees this
   reason in their app.

8. SHARED DETAIL ENDPOINT.
   /reimbursements/detail/ works for both admin and employee. Admin sees
   any claim in the org; employee sees only their own. Employee hitting
   someone else's claim → 404 (not 403) to avoid leaking existence.

SECTION — COMPANY EXPENSE ACCESS (batch 4)
================================================================================
Missing code -> 403 {"status": false, "message": "You do not have permission to perform this action."}
The organization owner has every code. Codes come from the caller's access role.

  create|list|detail|update|deactivate/          expense.manage
  recurring/* and recurring/entries/*            expense.manage
  Vendor dropdown: vendors/list/ accepts expense.manage too.
Default roles: Payroll Manager has expense.manage (and vendor.manage).
