================================================================================
PAYROLL APP — ADMIN API REFERENCE
================================================================================

Base URL   : /
Method     : All endpoints are POST
Auth       : Bearer token (IsAuthenticated)
Envelope   : { "status": true|false, "message": "...", "data": {...}?, "errors": {...}? }

Organization context:
  - All endpoints are scoped to the caller's organization via
    get_user_organization.
  - Do NOT send organization_id — it is ignored.

Who uses this document:
  - Organization owner (Admin role)
  - Any org member with Admin-level access (typically HR / finance)

This app has three audience tiers:
  - SUPER ADMIN (8)  — statutory rate configs + slabs (see SUPERADMIN doc)
  - ORG ADMIN (25)   — payroll lifecycle (THIS DOC)
  - EMPLOYEE (3)     — self-service (see EMPLOYEE doc)

This doc covers all 25 org-admin endpoints, split into 8 sections:
  1. Payroll Settings                 (1 endpoint)
  2. Company Statutory Settings       (1 endpoint)
  3. Salary Components                (2 endpoints)
  4. Salary Structures                (5 endpoints)
  5. Employee Salary Assignments      (5 endpoints)
  6. Payroll Runs                     (6 endpoints)
  7. Payroll Records                  (2 endpoints)
  8. Payroll Payments                 (3 endpoints)


================================================================================
BOOTSTRAP ORDER — READ FIRST
================================================================================

  1. Configure Payroll Settings          /settings/
  2. Configure Statutory Settings        /statutory-settings/
  3. Create Salary Components            /components/create/
  4. Create Salary Structures            /structures/create/
  5. Assign Structures to Employees      /assignments/create/ or /bulk-assign/
  6. (Optional) Preview a run            /runs/preview/
  7. Create a Payroll Run (DRAFT)        /runs/create/
  8. Generate the run                    /runs/generate/
  9. Review records + fix deductions     /records/list/, /records/update-deductions/
 10. Finalize the run                    /runs/finalize/
 11. Record payments                     /payments/record/ or /bulk-record/

  Steps 1–2 are one-time setup.
  Steps 3–5 are structure setup — repeat when policies change.
  Steps 6–11 are the monthly cycle.

  IMPORTANT:
    - Finalizing a run triggers a PAYSLIP_FINALIZED notification to every
      GENERATED record's employee.
    - Recording a payment triggers a PAYMENT_RECORDED notification to the
      employee.
    - Super-admin-managed statutory RATES and SLABS must already be in place
      globally before payroll computes correctly (see SUPERADMIN doc).

    "payroll_enabled": true,

    "created_at": "...",
    "updated_at": "..."

Request (UPDATE behavior — any of these keys):
{
  "cycle_start_day": 1,
  "default_pay_day": 15,
  "currency": "INR",
  "salary_basis": "CALENDAR_DAYS",
  "absent_deduction_multiplier": "1.00",
  "half_day_deduction_multiplier": "0.50",
  "unpaid_leave_multiplier": "1.00",
  "overtime_enabled": true,
  "overtime_rate_multiplier": "1.50",
  "late_deduction_enabled": false,
  "late_deduction_multiplier": "1.00",
  "standard_work_hours_per_day": "8.00",
  "missing_attendance_action": "ABSENT",
  "payslip_mode": "FULL",
  "payroll_enabled": true
}

LATE MARK DEDUCTION (batch 7)
  late_deduction_enabled     false (default) = late minutes are stored on the
                             payroll record but nothing is deducted
  late_deduction_multiplier  1.00 = deduct the late time at the normal rate;
                             2.00 = double. Not negative.
  Amount = late minutes x per-minute rate x multiplier
    per-minute rate = per_day_rate / (standard_work_hours_per_day x 60)
    (the same base as overtime). Example: 1000/day, 8 h -> 2.0833/min;
    120 late minutes x 1.00 = 250.00.
  Late minutes = attendance late_minutes (already after the late grace) of
  PRESENT days in the period. A day that became HALF_DAY (e.g. late beyond
  late_half_day_threshold_minutes) is deducted as a half day, not again as late.
  Payslip line: component_code "LATE", "Late Deduction", type DEDUCTION, in
  SIMPLE and FULL mode; calculation_details {late_minutes, rate_per_minute,
  rate_per_hour, multiplier, capped_to_zero_net}. Never takes net below 0.
  Does not change PF / ESI / PT bases (same as overtime).
  Record / preview / payslip carry "late_minutes"; breakdown has
  "late_minutes" and "late_deduction".

Response 200 (updated):
{
  "status": true,
  "message": "Payroll settings updated.",
  "data": { ...same shape with updated values... }
}

Response 400 (validation):
{
  "status": false,
  "message": "Invalid payroll settings.",
  "errors": {
    "cycle_start_day": ["cycle_start_day must be between 1 and 28."]
  }
}

Notes:
  - Auto-creates the settings row if not present (defaults apply).
  - Sending empty body {} OR {"organization_id": ...} alone acts as GET.
  - Any other key triggers UPDATE.
  - cycle_start_day range: 1–28.
  - default_pay_day range: 1–31.
  - All multipliers >= 0.
  - standard_work_hours_per_day > 0.

Enums:
  salary_basis              : CALENDAR_DAYS | FIXED_30 | WORKING_DAYS
  missing_attendance_action : REVIEW | ABSENT | SKIP
  payslip_mode              : SIMPLE | FULL

Enums:
  pf_contribution_type : STATUTORY | VPF | COMPANY_SPECIFIC

PF CONTRIBUTION TYPE (batch 8)
  STATUTORY         standard PF rates (rate configs with no organization, set by
                    the platform admin). Organization-specific configs are used
                    only if no standard config exists.
  COMPANY_SPECIFIC  this organization's own PF rate configs first (platform admin
                    creates them in statutory-rate-configs/create/ with
                    "organization": <id>, e.g. wage_ceiling null = PF on full
                    basic); standard rates for any code without one.
  VPF               standard rates + Voluntary PF: each employee's
                    vpf_percentage (employees/update/, 0-88) x the wage used for
                    employee PF -> extra employee deduction line "VPF"
                    ("Voluntary PF (Employee)"), stored in record.vpf_employee.
                    Employer PF / EPS / EDLI do not change. Employees with 0%
                    get no VPF line. VPF % is ignored for other types.
  Read-only "pf_rate_info" in the response:
    { "rates_used": "STANDARD" | "COMPANY", "standard_rate_configs": 4,
      "company_rate_configs": 0, "vpf_employees": 3,
      "note": "No company-specific PF rates yet: standard rates are used ..." }
  PF / ESI / PT / LWF are deducted only in payslip_mode FULL, for schemes switched
  on here, on salary components marked is_pf_eligible / is_esi_eligible.

4.2  POST /payroll/structures/create/
--------------------------------------------------------------------------------
Purpose : Create a salary structure with its components in one atomic call
Access  : Org Admin
Request :
{
  "name": "Standard Engineer",              // required, unique per org
  "code": "STD_ENG",                        // required, unique per org, auto upper
  "description": "Standard engineering package",
  "is_active": true,
  "components": [                           // required, non-empty list
    { "salary_component": 1, "amount": "30000.00", "percentage": null },
    { "salary_component": 2, "amount": "12000.00" },
    { "salary_component": 5, "percentage": "12.0000" }
  ]
}

Response 201:
{
  "status": true,
  "message": "Salary structure created.",
  "data": { ...full structure with components embedded... }
}

Response 400 (no components):
{ "status": false, "message": "components must be a non-empty list." }

Response 400 (header validation):
{
  "status": false,
  "message": "Invalid salary structure.",
  "errors": {
    "code": ["A structure with code 'STD_ENG' already exists."]
  }
}

Response 400 (component validation):
{
  "status": false,
  "message": "Invalid structure components.",
  "errors": [
    { "amount": ["Amount is required for FIXED components."] }
  ]
}

Response 400 (duplicate component id in list):
{ "status": false, "message": "Duplicate component ID 1 in structure." }

Component entry rules (enforced per entry):
  - salary_component : int id, must exist
  - component must be from this org OR global (organization=null)
  - component must be is_active=true
  - FIXED component   : "amount" required, "percentage" must be empty
  - PERCENTAGE component : "percentage" required, "amount" must be empty

Notes:
  - Atomic — if any component entry fails, the whole structure isn't created.
  - components is a nested list of objects (not flat ids).
  - Duplicate component IDs in the same structure are rejected.
  - code upper-cased + stripped automatically.
  - name and code must be unique per org, case-insensitive.
  - "is_active" defaults to true if omitted.

--------------------------------------------------------------------------------
5.2  POST /payroll/assignments/create/
--------------------------------------------------------------------------------
Purpose : Assign a salary structure to an employee
Access  : Org Admin
Request :
{
  "employee": 25,
  "salary_structure": 5,
  "effective_from": "2026-11-01",
  "effective_to": null,
  "reason": "Initial assignment"
}

Response 201:
{
  "status": true,
  "message": "Salary assignment created.",
  "data": { ...full assignment... }
}

Response 400 (overlap with existing):
{
  "status": false,
  "message": "Invalid salary assignment.",
  "errors": {
    "employee": [
      "Employee already has a salary assignment 'Standard Engineer' from 2026-01-01 to open-ended. Assignment date ranges cannot overlap."
    ]
  }
}

Response 400 (not on cycle boundary):
{
  "status": false,
  "message": "Invalid salary assignment.",
  "errors": {
    "effective_from": [
      "Salary assignment must start on a cycle boundary. The cycle containing 2026-11-15 starts on 2026-11-01. Use 2026-11-01 or a later cycle start as effective_from."
    ]
  }
}

Response 400 (invalid employee):
{
  "status": false,
  "message": "Invalid salary assignment.",
  "errors": {
    "employee": ["Only active/on-leave employees can be assigned a salary structure."]
  }
}

Response 400 (structure inactive or wrong org):
{
  "status": false,
  "message": "Invalid salary assignment.",
  "errors": {
    "salary_structure": ["Cannot assign an inactive salary structure."]
  }
}

Response 400 (bad date range):
{
  "status": false,
  "message": "Invalid salary assignment.",
  "errors": {
    "effective_to": ["End date cannot be before start date."]
  }
}

Notes:
  - effective_from MUST be a cycle boundary — i.e. it must equal the start
    day of the payroll cycle that contains that date (per
    PayrollSettings.cycle_start_day). This prevents mid-cycle salary
    revisions, which the calculation layer doesn't support.
  - Date ranges cannot OVERLAP for the same employee. A previous assignment
    must be closed (effective_to set) before starting a new one, OR the
    new one must start after the previous one ends.
  - employee must be active or ON_LEAVE in the caller's org.
  - salary_structure must be active and in the caller's org.
  - effective_to may be null (= open-ended).
  - If effective_to is provided, it must be >= effective_from.
  - assigned_by is auto-set to request.user.

7.2  POST /payroll/records/update-deductions/
--------------------------------------------------------------------------------
Purpose : Manually edit TDS / other deductions on one record, or recompute
Access  : Org Admin
Request (all optional — at least one of tds, other_deductions, review_notes
          or recompute=true must be provided):
{
  "payroll_record_id": 500,
  "tds": "500.00",
  "other_deductions": "100.00",
  "review_notes": "Adjusted per manager request",
  "recompute": false
}

Response 200:
{
  "status": true,
  "message": "Payroll record updated.",
  "data": { ...full record with recalculated net... }
}

Response 400 (no change specified):
{
  "status": false,
  "message": "Provide at least one of tds, other_deductions, review_notes, or recompute=true."
}

Response 400 (missing record_id):
{ "status": false, "message": "payroll_record_id is required." }

Response 400 (invalid number):
{ "status": false, "message": "tds must be a valid number." }

{
  "status": false,
  "message": "Cannot modify a record in a finalized payroll run."
}

Response 404:
{ "status": false, "message": "Payroll record not found." }

Response 500:
{ "status": false, "message": "Unable to update payroll record." }

    attendance + salary assignment + statutory rates. USE WITH CARE:
    it overrides any manual edits you made previously to TDS or
    other_deductions on this record.

    record's breakdown JSON is refreshed.

    the response reflects the post-update state (paid_amount, net,
    remaining).

      * another /records/update-deductions/ with recompute=true
      * another /runs/generate/ (regenerates the record entirely)
  - Typical workflow:
      1. /records/list/ filter generation_status=GENERATED, requires_review=true
      2. For each flagged record → /records/update-deductions/ with
         recompute=false + corrected tds/other_deductions
      3. /runs/finalize/ once all records look right

{ "status": false, "message": "employee_ids must be a non-empty list when provided." }

{ "status": false, "message": "Payroll run not found." }

Response 500:
{ "status": false, "message": "Unable to record bulk payment." }

  - If "employee_ids" is PROVIDED → pays only those employees (useful for
    excluding employees whose payment is pending).
  - Per record, the full net amount is paid — for PARTIAL payment,
    use /payments/record/ individually.
  - The run must be FINALIZED before payments can be recorded (the
    service enforces this per-record; if the whole run isn't finalized,
    all payments fail).
  - SIDE EFFECT — fires a PAYMENT_RECORDED notification per paid employee
    (same shape as 8.1). Uses the same transaction.on_commit pattern with
    closure capture per iteration so each notification has the correct
    amount/period/mode/remaining values.
  - Bulk operations are atomic at the service level — if any payment
    raises an unexpected error, the response includes it under "errors"
    but earlier payments are NOT rolled back (per-record transaction).

================================================================================
KEY NOTES FOR FRONTEND / UI DESIGNER
================================================================================

1. THIS APP IS ORG-ADMIN ONLY.
   The super-admin endpoints (statutory rate configs + slabs) are in a
   separate SUPERADMIN doc. Employee self-service is in a separate
   EMPLOYEE doc. This doc is only the 25 payroll lifecycle endpoints
   that the admin panel calls.

2. THE PAYROLL LIFECYCLE IS STATE-MACHINED.
   Run states: DRAFT → GENERATED → FINALIZED.
     - DRAFT: created, no records yet. Can be re-generated anytime.
     - GENERATED: records computed. Can edit deductions, then finalize.
     - FINALIZED: immutable. Payslips sent to employees. Only payments
       can be recorded after this.
   UI must gate buttons by state:
     - DRAFT run: show "Generate" button only
     - GENERATED run: show "Finalize" button, edit deductions, delete
     - FINALIZED run: show "Record Payment" / "Bulk Record" only

3. CYCLE BOUNDARY IS A HARD CONSTRAINT.
   Salary assignments MUST start on the org's cycle_start_day. If the
   org's cycle starts on the 1st and admin tries to assign starting on
   the 15th, it 400s. The error message tells you exactly which cycle
   start date to use instead.

4. NO OVERLAPPING ASSIGNMENTS.
   An employee can have MULTIPLE sequential assignments (e.g. old one
   ends Dec 31, new one starts Jan 1), but two assignments on the same
   employee cannot overlap in date range. To revise a salary:
     1. /assignments/bulk-close/ (or update) the old assignment with
        effective_to = day before the new one starts
     2. /assignments/create/ the new assignment with effective_from =
        the new cycle start
   The UI should offer this two-step flow as a single "Revise Salary"
   action.

5. STRUCTURAL EDIT BLOCK ON FINALIZED RUNS.
   If an assignment appears in a FINALIZED run:
     - salary_structure and effective_from CANNOT be changed
     - other fields (effective_to, reason) still editable
   This protects historical payroll from retroactive mutation.

6. RECOMPUTE IS DESTRUCTIVE.
   /records/update-deductions/ with recompute=true wipes manual TDS /
   other_deductions overrides and recalculates from scratch. This is
   the "reset to system-computed value" button — warn the admin before
   they click it.

7. FINALIZE SENDS NOTIFICATIONS.
   Calling /runs/finalize/ triggers a PAYSLIP_FINALIZED push + bell row
   per GENERATED record. You cannot un-send. Make sure the run is
   correct BEFORE finalizing. There is no "unfinalize" endpoint — a
   correction requires a new run.

8. PAYMENT RECORDING SENDS NOTIFICATIONS.
   Both /payments/record/ and /payments/bulk-record/ trigger
   PAYMENT_RECORDED notifications. For partial payments, employees get
   one notification per payment with the updated remaining balance.

9. PAYMENT ONLY AFTER FINALIZE.
   Recording a payment on a DRAFT or GENERATED run 400s. The UI should
   only show payment buttons when run.status = FINALIZED.

10. BULK OPERATIONS ARE ATOMIC.
    /assignments/bulk-assign/ and /assignments/bulk-close/ roll back
    the ENTIRE batch on any single failure. Show the error clearly and
    let admin fix the offending employee, then retry.
    /payments/bulk-record/ is per-record atomic (earlier payments stick
    even if later ones fail) — errors come back in the "errors" array.

11. NO PAGINATION ANYWHERE.
    All list endpoints return the full filtered list. For large orgs:
      - Always filter /records/list/ by payroll_run_id
      - Always filter /payments/list/ by payroll_run_id or date range
      - The /runs/detail/ response is the heaviest (embeds all records)
        — for 500+ employees this can be megabytes. Consider using
        /records/list/?payroll_run_id=X for list views instead of
        the full detail.

12. UPI LINK IN RECORDS.
    Each PayrollRecord includes a "upi_link" field (if the employee has
    a upi_id and remaining > 0). This is a upi:// deep-link the UI can
    surface as a "Pay via UPI" QR/button for one-off manual payment.
    Format:
      upi://pay?pa=<upi_id>&pn=<name>&am=<remaining>&cu=INR&tn=<note>
    Only relevant if the admin chooses to pay individually — bulk
    payments go through /payments/bulk-record/ and don't use this link.

13. ITEMS TO VERIFY IN CODE BEFORE SHIPPING.
    - /payments/list/ view code not seen in the reviewed files — the
      filter params documented here are inferred. Confirm against the
      actual view if filters behave unexpectedly.
    - The default value for "recompute" in /records/update-deductions/
      is false. If the UI sends "recompute": "true" (string), the
      backend handles it via parse_bool — but nulls and empty strings
      default to false. Send a real JSON boolean for reliability.

Payroll Calculator API

Read-only what-if calculator. It works out a payslip from day counts typed by the admin, using the same rules as a real payroll run. Nothing is saved: no payroll run, record, payment, attendance or audit entry is created or changed, and the saved payroll settings are never modified.

Response envelope: { "status": bool, "message": str, "data": object | null, "errors"?: ... }

weekly_off_days	number	no, default 0	Paid, not deducted

SECTION — CTC / AGREED PACKAGE (batch 3)
================================================================================

Pay is never tied to designation / department. Each salary assignment (and
each offer) can carry the agreed package; the structure is then a template.

New fields
  PayrollSettings.ctc_includes_employer_contributions   bool, default true
      true : annual CTC = 12 x (monthly gross + employer PF + EDLI + ESI employer + LWF employer)
      false: annual CTC = 12 x monthly gross
      Employer PF is the PF_EMPLOYER rate (12 %, it already contains the EPS
      split, so EPS is not added again). Employer costs count only in FULL
      payslip mode with the scheme enabled in statutory settings.
  SalaryStructureComponent.is_balancing                 bool (one per structure)
      This earning receives "monthly gross minus every other earning".
  EmployeeSalaryAssignment.annual_ctc, monthly_gross    decimals, optional

How a structure works with a monthly gross
  - PERCENTAGE component with no base component  -> % of monthly gross
  - PERCENTAGE of another component              -> as before
  - FIXED                                        -> as before
  - balancing earning                            -> the rest
  Example "Developer": Basic 50 % (of gross), HRA 40 % of Basic,
  Conveyance 1600 fixed, Special = balancing.
  Gross 50,000 -> Basic 25,000, HRA 10,000, Conveyance 1,600, Special 13,400.
  Assignments WITHOUT annual_ctc / monthly_gross work exactly as before.
  If the structure cannot reach the agreed gross (no balancing earning,
  fixed parts too large) the payroll record gets a review warning.

--------------------------------------------------------------------------------

Both payslip modes list every line of the record (no totals-only view):
  Attendance  present, half days, absent, paid / unpaid leave, holidays,
              weekly offs, overtime hours, Late Time ("1 h 20 min" from late_minutes)
  Earnings    FULL: each salary component + Overtime
              SIMPLE: "Gross Salary" + Overtime (if any)
  Deductions  PF, VPF, ESI, PT, LWF (FULL only), TDS / other deductions (manual,
              both modes), Late Deduction, Loss of Pay; then Total Deductions
  Employer Statutory Contributions: FULL only
Lines with 0 are not written (no OT line when there is no overtime, etc.).
