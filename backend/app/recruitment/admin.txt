================================================================================
RECRUITMENT APP — ADMIN / HR API REFERENCE
================================================================================

Base URL   : /recruitment/
Method     : All endpoints are POST
Auth       : Bearer token
Envelope   : { "status": true|false, "message": "...", "data": {...}?, "errors": {...}? }
Org        : single-org users omit organization_id; multi-org users send it.
Body type  : JSON. create/ and update/ also accept multipart (files); then send
             lists / objects (education, experience, interviews) as JSON strings.

WORKFLOW (one applicant row, three stages)
  stage   APPLICANT -> VERIFICATION -> ONBOARDING -> COMPLETED      (CLOSED = rejected / withdrawn)
  status  PENDING | SHORTLISTED | SELECTED | REJECTED | WITHDRAWN

  APPLICANT     PENDING <-> SHORTLISTED ; -> SELECTED (moves to VERIFICATION)
                -> REJECTED / WITHDRAWN (moves to CLOSED)
  VERIFICATION  checklist + offer. Offer accepted + checklist done -> complete -> ONBOARDING
  ONBOARDING    joining details + checklist -> convert -> COMPLETED (employee created)
  CLOSED        can be reopened to PENDING (back to APPLICANT). Never convertible.
  REJECTED / WITHDRAWN from VERIFICATION or ONBOARDING also revokes open offers.

PERMISSIONS (access role codes; the organization owner has all)
  applicant.view            list, detail
  applicant.create          create
  applicant.update          update
  applicant.status_update   status-update
  verification.update       verification (checks, offer, complete)
  onboarding.complete       onboarding, convert
  access.manage             needed to set access_role_id in onboarding
  employee.create_user      needed for the login created on convert
  Users with ONLY applicant.view (default: Department Manager) see applicants
  assigned to them or where they are an interviewer, and can only record
  result / rating / feedback on their own interviews.

--------------------------------------------------------------------------------
1. POST /recruitment/applicant/create/            applicant.create
--------------------------------------------------------------------------------
Required: first_name, last_name, email, mobile
Optional: middle_name, alternate_mobile, date_of_birth, gender (MALE|FEMALE|OTHER),
  address, city, state_id, pincode,
  designation_id, position_title (free text), department_id, branch_id,
  source (JOB_PORTAL|REFERRAL|WEBSITE|WALK_IN|CAMPUS|AGENCY|SOCIAL|OTHER),
  referred_by_id (employee), assigned_to_id (employee id, from the employee list), applied_on (default today),
  total_experience_years, current_company, current_designation, current_ctc,
  expected_ctc, notice_period_days, skills, remarks,
  education [ {degree, institution?, year?, score?} ],
  experience [ {company, designation?, from_date?, to_date?, ctc?, reason_for_leaving?} ]
Files (multipart): resume (stored as RESUME), documents[] + document_types[]
  (RESUME|ID_PROOF|ADDRESS_PROOF|EDUCATION|EXPERIENCE|PAYSLIP|PHOTO|OFFER_LETTER|OTHER)
201 -> detail object. 400 duplicate: "An open applicant with this email or mobile
already exists (APL-...)." or "An active employee with this email or mobile already exists (EMP-...)."

2. POST /recruitment/applicant/list/              applicant.view
--------------------------------------------------------------------------------
Filters (all optional): search (code, name, email, mobile, position, skills),
  stage, status, source, designation_id, department_id, branch_id,
  assigned_to_id, assigned_to_me (true), applied_from, applied_to (YYYY-MM-DD)
200 { "data": [ {id, applicant_code, full_name, email, mobile, designation, position_title,
                 department, branch, source, applied_on, total_experience_years,
                 expected_ctc, stage, status, assigned_to, joining_date, employee, created_at} ],
      "summary": {"total": 42,
                  "by_stage":  {"APPLICANT": 25, "VERIFICATION": 5, "ONBOARDING": 2, "COMPLETED": 8, "CLOSED": 2},
                  "by_status": {"PENDING": 12, "SHORTLISTED": 10, "SELECTED": 15, "REJECTED": 4, "WITHDRAWN": 1}} }
summary counts follow "search" but not the other filters (tiles stay stable).

4. POST /recruitment/applicant/update/            applicant.update
--------------------------------------------------------------------------------
{ "applicant_id": 7, ...only the fields that change (same names as create),
  "interviews": [ {"id"?: 3, "round_name", "scheduled_at", "mode": IN_PERSON|PHONE|VIDEO,
                   "interviewer_id", "result": SCHEDULED|PASSED|FAILED|ON_HOLD|NO_SHOW|CANCELLED,
                   "rating": 1-5, "feedback"} ],     id = update, no id = add
  "remove_interview_ids": [..], "remove_document_ids": [..] }  + files as in create
Interviewer with only applicant.view: send just
  { "applicant_id", "interviews": [ {"id", "result", "rating", "feedback"} ] }
  (other fields ignored; another person's interview -> 403).
Converted (COMPLETED) applicants cannot be edited -> 400.

--------------------------------------------------------------------------------
5. POST /recruitment/applicant/status-update/     applicant.status_update
--------------------------------------------------------------------------------
{ "applicant_id": 7, "status": "SHORTLISTED" | "SELECTED" | "REJECTED" | "WITHDRAWN" | "PENDING", "note"? }
SELECTED creates the verification checklist. Not allowed move -> 400
"Cannot change status from X to Y while the applicant is in STAGE."

--------------------------------------------------------------------------------
6. POST /recruitment/applicant/verification/      verification.update
--------------------------------------------------------------------------------
Every part is optional; they run in this order: offer, offer_action, checks, complete.
{
  "applicant_id": 7,
  "offer": { "salary_structure_id": 2, "joining_date": "2026-12-10",
             "annual_ctc": "700000" | "monthly_gross": "52000",
             "designation_id"?, "department_id"?, "branch_id"?, "notes"?,
             "probation_months"? (0-36), "notice_period_days"? (0-365),
             "valid_until"? (YYYY-MM-DD, today or later: last day to respond) },
  "offer_action": "SEND" | "ACCEPT" | "DECLINE" | "REVOKE", "offer_note"?,
  "send_email"?: true (default) | false,  "email_message"?: "text shown in the mail",
  "checks": [ {"key": "IDENTITY", "status": "DONE"|"PENDING"|"REJECTED"|"WAIVED", "note"?},
              {"key": "POLICE", "label": "Police verification", "status": "DONE"} ],   new key + label = extra line
  "complete": true
}
Checklist: PERSONAL_DETAILS, IDENTITY, EDUCATION, EXPERIENCE (manual),
           SALARY_OFFER, OFFER_ACCEPTANCE (automatic: is_system = true, cannot be set by hand).
Offer rules:
  - offer terms never change; sending "offer" again creates version n+1 and marks
    the open one SUPERSEDED. The breakup snapshot is taken from the payroll calculator.
  - send annual_ctc or monthly_gross; the other is worked out (payroll/admin.txt CTC).
  - DRAFT -> SENT -> ACCEPTED | DECLINED ; DRAFT/SENT -> REVOKED.
  - SEND emails the candidate: email_message + offer letter PDF attached + a link
    to accept or decline in the browser (section 10). Reply-to = organization email.
  - SEND again while SENT = resend the mail (same link); email_count goes up and
    each mail is in history (OFFER_EMAILED). send_email=false: mark SENT, no mail.
  - Mail errors -> 400 "Unable to send the offer email: ..." (candidate email missing, SMTP).
  - ACCEPT / DECLINE here = HR records the answer for the candidate (responded_via HR).
  - Once ACCEPTED or DECLINED (by HR or the candidate) the answer cannot be changed;
    to change terms after a decline, create a new offer version.
complete: needs the current offer ACCEPTED and every check DONE or WAIVED; moves to
ONBOARDING, copies joining date / designation / department / branch from the offer and
creates the onboarding checklist. Otherwise 400 "Verification is not complete: Identity documents, ..."

--------------------------------------------------------------------------------
8. POST /recruitment/applicant/convert/           onboarding.complete
--------------------------------------------------------------------------------
{ "applicant_id": 7, "create_user"?: true|false }
create_user default: true when the caller has employee.create_user, else false.
One transaction:
  1. Employee (EMP-xxxxxx) from the applicant + onboarding details, ACTIVE,
     joining_date, branch / department / designation / manager / access role;
     documents copied to employee documents.
  2. Salary assignment from the ACCEPTED offer (structure, annual_ctc, monthly_gross),
     effective_from = start of the payroll cycle that contains the joining date.
     Days before joining are unpaid through attendance (not_employed_days).
  3. Login (username = employee code, role Employee, membership); credentials email
     is sent after commit.
  4. Leave balances for the joining year (every active leave type, full allocation).
  5. Applicant -> COMPLETED, history CONVERTED.
Needs: stage ONBOARDING + status SELECTED, accepted offer, joining date, manual
onboarding checks DONE/WAIVED, payroll settings configured.
201 data = detail object + "salary_assignment": {id, effective_from, annual_ctc,
monthly_gross, salary_structure_id} + "user_account": {user_id, username, email} | null
Errors 400: "Onboarding is not complete: ...", "The applicant has no accepted offer.",
"This applicant is already an employee.", "Payroll settings are not configured; ...",
user errors (email / mobile already used) under errors.

--------------------------------------------------------------------------------
9. POST /recruitment/applicant/offer-letter/download/   verification.update | onboarding.complete
--------------------------------------------------------------------------------
{ "applicant_id": 7, "offer_id"?: 12 }      default = current offer (any status, also DRAFT)
200 -> application/pdf file (Content-Disposition attachment, Offer_Letter_<code>_V<n>.pdf).
Errors use the JSON envelope (404 no offer, 403 no permission).
Letter: organization logo, name, address, GSTIN, email, phone; candidate; reference
<code>/OFFER/V<n>; position, department, branch, joining date, probation, notice
period, respond-by date; CTC breakup (earnings, gross, employer contributions, CTC);
notes. Template: app/recruitment/templates/offer_letter.html

--------------------------------------------------------------------------------
10. CANDIDATE PAGES (browser, no login)                 #PUB
--------------------------------------------------------------------------------
GET  /recruitment/offer/<token>/          page with the offer terms, PDF link and
                                          Accept / Decline buttons (+ optional note)
POST /recruitment/offer/<token>/          form: action=ACCEPT|DECLINE, note?  (CSRF form,
                                          served by the same page; not a JSON API)
GET  /recruitment/offer/<token>/letter/   offer letter PDF
The link is in the offer email. Page states:
  OPEN      buttons shown
  ACCEPTED / DECLINED   the recorded answer, no buttons (final, cannot be changed)
  EXPIRED   valid_until has passed
  CLOSED    revoked or replaced by a newer version (PDF link also closed)
Unknown token -> 404 page. A second answer -> 400 page "You have already accepted this offer."
On answer: offer ACCEPTED/DECLINED (responded_via CANDIDATE, response_note), the
OFFER_ACCEPTANCE check is set, history entry, and a notification (OFFER_ACCEPTED /
OFFER_DECLINED) goes to the offer creator, the assigned employee, the owner and
verification.update holders.
Link host = the host HR used when sending (request host); behind a proxy forward
the Host header so the link points to the public domain.
