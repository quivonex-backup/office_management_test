================================================================================
ACCOUNTS / ORGANIZATION APP — API REFERENCE FOR FRONTEND
================================================================================

Base URL       : /
Method         : All endpoints are POST
Auth           : Bearer token (IsAuthenticated) unless noted PUBLIC
Envelope       : { "status": true|false, "message": "...", "data": {...}?, "errors": {...}? }

Roles:
  - #SU  = Super Admin  (user.is_superuser == true)
  - #A   = Admin / Company Owner (organization.owner)
  - #E   = Employee (any authenticated org member)
  - #PUB = Public (no auth required)

Organization context:
  - If the logged-in user belongs to exactly one active organization,
    organization context is auto-resolved.
  - If the user belongs to multiple organizations, request body must
    include "organization_id".
  - Super admins bypass org scoping on list/detail endpoints and see
    everything.


================================================================================
BOOTSTRAP ORDER — READ THIS FIRST
================================================================================
Data must exist in this order for the rest of the system to work:

  STEP 0 (super admin — one time for the platform)
    └─ 1. Create Roles                 (Admin, Accountant, etc.)
    └─ 2. Create Organizations         (each tenant)
    └─ 3. Assign Organization Owner    (Admin role + membership)

  STEP 1 (org admin — one time per organization)
    └─ 4. Update organization profile  (logos, address, contact)
    └─ 5. Register / assign users      (super admin creates users)
    └─ 6. Assign members to org        (owner assigns roles)

  STEP 2 (any user — anytime)
    └─ 7. Login / refresh token
    └─ 8. View own profile / update it
    └─ 9. Change password
    └─ 10. View own organizations

  STEP 3 (optional — OTP flows)
    └─ 11. Send OTP / Verify OTP       (registration, forgot password)

IMPORTANT:
  - Roles are global (shared across all organizations).
  - A user can belong to AT MOST ONE active organization (enforced).
  - "Admin" role is reserved for organization owners and must be
    assigned via the assign-owner API, not assign-user.
  - "Accountant" role is used when downgrading a previous owner.

Purpose : Authenticate and receive JWT tokens.

Request:

  "username": "rahul",
  "password": "SecurePass@123"
}

Response 200:
{
  "status": true,
  "message": "Login successful.",
  "data": {
    "access": "eyJ0eXAiOiJKV1Qi...",
    "refresh": "eyJ0eXAiOiJKV1Qi...",
    "user": {
      "id": 25,
      "username": "rahul",
      "first_name": "Rahul",
      "last_name": "Patil",
      "email": "rahul@example.com",
      "mobile": "9876543210",
      "profile_photo": "users/profile/abc.jpg",
      "role": 1,
      "role_details": {
        "id": 1,
        "name": "Admin",
        "is_active": true,
        "created_at": "...",
        "updated_at": "..."
      },
      "is_active": true,
      "date_joined": "...",
      "created_at": "...",
      "updated_at": "..."
    }
  }
}

Response 400: { "status": false, "message": "Username and password are required." }
Response 401: { "status": false, "message": "Invalid username or password." }
Response 403: { "status": false, "message": "Your account is inactive." }

NOTE:
  - A LOGIN audit log is written on every successful login.
  - Frontend must store "access" and "refresh" and send
    "Authorization: Bearer <access>" on every subsequent request.

--------------------------------------------------------------------------------
1.2  POST /forgot-password/
--------------------------------------------------------------------------------
Auth : #PUB
Purpose : Reset password by email (no OTP required — email match only).

Request:
{
  "email": "rahul@example.com",
  "new_password": "NewPass@123",
  "confirm_password": "NewPass@123"
}

Response 200:
{
  "status": true,
  "message": "Password reset successfully. Please login with your new password.",
  "data": null
}

Response 400: { "status": false, "message": "Validation failed.", "errors": {...} }
Response 404: { "status": false, "message": "User not found." }

NOTE:
  - Password is validated by Django password validators.
  - A PASSWORD_RESET audit log is written.

--------------------------------------------------------------------------------
1.3  POST /send-otp/
--------------------------------------------------------------------------------
Auth : #PUB
Purpose : Send a 6-digit OTP to an email (for verification flows).

Request:
{
  "email": "rahul@example.com",
  "purpose": "EMAIL_VERIFICATION"
}

purpose values (optional):
  EMAIL_VERIFICATION | FORGOT_PASSWORD | LOGIN | CHANGE_EMAIL

Response 200:
{
  "status": true,
  "message": "OTP sent successfully.",
  "data": { "expires_at": "2026-03-15T10:35:00Z" }
}

Response 500: { "status": false, "message": "Unable to send OTP. Please try again." }

NOTE:
  - OTP expires in 5 minutes.
  - Any previous unverified OTP for this email/purpose is expired.
  - If email sending fails, the OTP record is expired immediately.

--------------------------------------------------------------------------------
1.4  POST /verify-otp/
--------------------------------------------------------------------------------
Auth : #PUB
Purpose : Verify an OTP previously sent.

Request:
{
  "email": "rahul@example.com",
  "otp": "123456",
  "purpose": "EMAIL_VERIFICATION"
}

Response 200:
{
  "status": true,
  "message": "OTP verified successfully.",
  "data": null
}

Response 400 variants:
  { "status": false, "message": "No OTP found. Please request a new OTP." }
  { "status": false, "message": "OTP has expired. Please request a new OTP." }
  { "status": false, "message": "Maximum OTP attempts exceeded. Please request a new OTP." }
  { "status": false, "message": "Invalid OTP.", "data": { "remaining_attempts": 3 } }

NOTE:
  - Max 5 attempts per OTP.
  - OTP must be exactly 6 digits.

================================================================================
KEY NOTES FOR FRONTEND TEAM
================================================================================

1. RESPONSE ENVELOPE
   Every response:
     { "status": true|false, "message": "...", "data": {...}? }
   Validation failures add:
     { "errors": { "field": ["msg", ...] } }
   Always check "status" before reading "data".

2. AUTH HEADER
   Send "Authorization: Bearer <access>" on every non-public endpoint.
   On 401, use the refresh token to obtain a new access token.

3. ROLE HIERARCHY (as intended)
   - #SU (is_superuser)         → super admin; manages tenants & users.
   - #A  (organization.owner)   → tenant admin; manages own org.
   - #E  (any member)           → employee; self-service only.

4. ONE-ACTIVE-ORG-PER-USER RULE
   A user may belong to exactly ONE active organization at a time.
   Attempting to assign a user who already belongs to another active
   organization returns HTTP 400. To move a user, the previous
   membership must be deactivated first (no API currently exposes this —
   it's implicit via owner change).

5. OWNER vs MEMBER
   - Owner is stored on Organization.owner (FK to User).
   - Owner's User.role must be "Admin".
   - Members are stored in OrganizationMembership (no role field).
   - Member's User.role is whatever was passed in assign-user.

6. SOFT DELETE
   - Users, Roles, Organizations are never hard-deleted.
   - is_active = False hides them from list/detail endpoints.

7. PROFILE PHOTOS & LOGOS
   - Uploaded to S3 first, then path stored in DB.
   - On save failure, the new S3 object is deleted.
   - On successful save, the old S3 object is deleted.
   - Serializer returns the S3 path (frontend must build full URL
     via your S3/CDN helper).

8. PASSWORD FLOWS
   - Registration sends plain password via email (one-time).
   - Forgot-password is email-only — no OTP requirement currently.
   - Change-password requires old password.
   - Django password validators are enabled on forgot-password
     but DISABLED on change-password (commented in view).

9. OTP BEHAVIOR
   - 6 digits, 5-minute expiry, 5 max attempts.
   - Purpose is optional but recommended for scoping.
   - Previous unverified OTPs for same email/purpose are auto-expired.

10. AUDIT LOGGING
    Every mutating endpoint writes a log_activity row with:
      action (CREATE / UPDATE / DELETE / LOGIN / PASSWORD_CHANGE /
              PASSWORD_RESET), module, object_type, object_id,
      description, old_data, new_data.
    Passwords are NEVER included in audit data.

11. ORGANIZATION CODE
    - Auto-generated on create (format defined in code_generators).
    - Read-only on the serializer.
    - Unique across all organizations.

12. WHERE THE CODE DOESN'T MATCH TAGS
    Before going to production, add permission classes for:
      - /register/                → IsSuperAdmin
      - /user/* (4 endpoints)     → IsSuperAdmin
      - /role/* (5 endpoints)     → IsSuperAdmin
    Currently they rely only on IsAuthenticated, so any logged-in
    employee can list users, promote themselves to Admin via
    user/update/, deactivate users, and manage roles.

    Super admin also cannot update/deactivate an org they don't own —
    the views filter by owner=request.user only. If super admin should
    bypass, add "Q(owner=request.user) | is_super_admin".
