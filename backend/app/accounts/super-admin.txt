================================================================================
ACCOUNTS / ORGANIZATION APP — SUPER ADMIN API REFERENCE
================================================================================

Base URL       : /
Method         : All endpoints are POST
Auth           : Bearer token (IsAuthenticated) unless marked PUBLIC
Envelope       : { "status": true|false, "message": "...", "data": {...}?, "errors": {...}? }

Who uses this document:
  - Super Admin only (user.is_superuser == true)
  - Platform operators who manage tenants, users, and roles

What Super Admin owns:
  - Creating and managing organizations (tenants)
  - Creating and managing all users (employees, admins)
  - Managing the global role catalog
  - Assigning organization owners
  - Assigning users to organizations

What Super Admin DOES NOT do here:
  - Employee self-service (login, my-profile, OTP) — see EMPLOYEE doc
  - Org-specific business operations (projects, expenses, payroll, etc.)
    — those require org membership even for super admin to act on


================================================================================
BOOTSTRAP ORDER — PLATFORM SETUP
================================================================================

  STEP 1 — Roles (once, globally)
    └─ POST /accounts/role/create/
       Create "Admin", "Accountant", "Employee" (and any others)

  STEP 2 — Organizations (one per tenant)
    └─ POST /accounts/organization/create/

  STEP 3 — Users (one per person on the platform)
    └─ POST /accounts/register/

  STEP 4 — Assign owners (one per organization)
    └─ POST /accounts/organization/assign-owner/
       → creates the Admin role + membership for that user

  STEP 5 — Assign additional users to orgs (optional)
    └─ POST /accounts/organization/assign-user/

CRITICAL RULES:
  - Roles are GLOBAL, shared by all organizations.
  - A user can belong to AT MOST ONE active organization (enforced).
  - "Admin" role is reserved for organization owners — you cannot
    assign it via assign-user, only via assign-owner.
  - "Accountant" role is used when the system downgrades a previous
    owner who was replaced by a new owner.


================================================================================
SECTION 1 — AUTHENTICATION (SUPER ADMIN + SHARED)
================================================================================

Super admin logs in through the SAME endpoint as everyone else. The
role is distinguished by is_superuser = true on their User row.

--------------------------------------------------------------------------------
1.1  POST /accounts/login/
--------------------------------------------------------------------------------
Auth : PUBLIC
Purpose : Authenticate. Returns JWT + user object.

Request :
{
  "username": "superadmin",
  "password": "SecurePass@123"
}

Response 200:
{
  "status": true,
  "message": "Login successful.",
  "data": {
    "access": "eyJ0eXAi...",
    "refresh": "eyJ0eXAi...",
    "user": {
      "id": 1,
      "username": "superadmin",
      "first_name": "Platform",
      "last_name": "Admin",
      "email": "superadmin@platform.com",
      "mobile": "9999999999",
      "profile_photo": "users/profile/su.jpg",
      "role": 1,
      "role_details": {
        "id": 1,
        "name": "Admin",
        "is_active": true,
        "created_at": "...",
        "updated_at": "..."
      },
      "is_active": true,
      "date_joined": "...",
      "created_at": "...",
      "updated_at": "..."
    }
  }
}

NOTE: The `is_superuser` flag is NOT in this serializer output by
      default. The backend detects it from the token's user_id on
      every request. The frontend may need a way to distinguish
      super admin from regular admin — see note 10 in the summary
      section below.

Responses 400 / 401 / 403 : same as employee doc.

--------------------------------------------------------------------------------
1.2  POST /accounts/refresh-token/
--------------------------------------------------------------------------------
Auth : PUBLIC
Purpose : Exchange a valid refresh token for a new access + refresh pair.

Request :
{ "refresh": "eyJ0eXAi..." }

Response 200:
{
  "status": true,
  "message": "Token refreshed successfully.",
  "data": {
    "access": "eyJ0eXAi...new...",
    "refresh": "eyJ0eXAi...new..."
  }
}

IMPORTANT — REFRESH ROTATION IS ON:
  - The OLD refresh token is blacklisted on success.
  - The OLD access token stays valid until natural expiry.
  - You MUST overwrite BOTH stored tokens.
  - Reusing the old refresh token → 401 "Invalid or expired refresh token."

Response 401 (invalid/expired/blacklisted):
{ "status": false, "message": "Invalid or expired refresh token. Please login again." }

Response 401 (user deactivated):
{ "status": false, "message": "User not found or inactive." }

2.5  POST /accounts/user/deactivate/
--------------------------------------------------------------------------------
Auth : #SU   ⚠ currently any authenticated user — will be locked
Purpose : Soft-delete a user (sets is_active=false).

Request : { "id": 30 }

Response 200:
{
  "status": true,
  "message": "Account deactivated successfully.",
  "data": null
}

Response 404: { "status": false, "message": "Account not found or already inactive." }

NOTE:
  - Row is preserved; only is_active flips.
  - The user can no longer log in (login endpoint returns 403).
  - Audit log "DELETE USER" with old/new.
  - ⚠ Deactivating a user does NOT deactivate their OrganizationMembership
    or their Employee record — those remain active. The deactivation only
    blocks login. Business records still reference them.

4.5  POST /accounts/organization/assign-owner/
--------------------------------------------------------------------------------
Auth : #SU (enforced)
Purpose : Assign an Admin (owner) to an organization.

Request :
{
  "organization_id": 5,
  "user_id": 25
}

Response 200:
{
  "status": true,
  "message": "Organization owner assigned successfully.",
  "data": {
    "organization_id": 5,
    "organization_name": "Acme Pvt Ltd",
    "owner_id": 25,
    "owner_username": "rahul",
    "owner_email": "rahul@example.com",
    "role_id": 1,
    "role": "Admin",
    "membership_id": 12,
    "membership_created": true
  }
}

Response 400 variants:
{ "status": false, "message": "organization_id and user_id are required." }
{ "status": false, "message": "Active Admin and Accountant roles must exist." }
{ "status": false, "message": "This user already belongs to another active organization." }

Response 403:
{ "status": false, "message": "Only the super admin can assign an organization owner." }

Response 404:
{ "status": false, "message": "Organization not found or inactive." }
{ "status": false, "message": "User not found or inactive." }

NOTE:
  - Wrapped in transaction.atomic with select_for_update on org and user.
  - If the org already had a different owner:
      * Previous owner's role downgrades to "Accountant"
      * Previous owner's membership stays active
  - New owner gets Admin role + active membership.
  - Idempotent: calling again for the SAME user creates nothing new
    (membership_created=false).
  - Audit log "UPDATE ORGANIZATION".

================================================================================
KEY NOTES FOR FRONTEND — SUPER ADMIN SIDE
================================================================================

1. IS_SUPERUSER IS NOT IN THE USER SERIALIZER
   The login/my-profile response does NOT include an is_superuser field.
   The frontend must either:
     a) Treat the super admin's username as a known constant from config
        (fragile), OR
     b) Ask the backend team to add "is_superuser" to UserSerializer
        (recommended — one-line addition).
   Without this, the frontend cannot distinguish a super admin from a
   regular admin by their user object alone.

2. THE "ADMIN" ROLE IS NOT THE SAME AS SUPER ADMIN
   - Super admin = user.is_superuser == true (Django flag)
   - Admin = the organization.owner of a specific org
   A user can be an Admin (org owner) WITHOUT being a super admin.
   Super admin usually has NO organization membership at all.

3. ROLES ARE GLOBAL
   The roles you create (Admin, Accountant, Employee) are shared across
   every organization on the platform. Renaming "Accountant" affects
   every org's UI labels.

4. ONE-ACTIVE-ORG-PER-USER
   Assigning a user who already belongs to another active org returns
   400. There is NO endpoint to deactivate a membership yet — this is a
   gap. Workarounds: promote them as owner of another org (downgrades
   previous), or use direct DB admin for now.

5. SOFT DELETE EVERYWHERE
   Users, Roles, Organizations are never hard-deleted.
   is_active=false hides them from list endpoints.

6. "ACCOUNTANT" ROLE IS LOAD-BEARING
   When assigning a new owner to an org that already has one, the
   system downgrades the previous owner to "Accountant". This role
   MUST exist or /assign-owner/ returns 400 "Active Admin and
   Accountant roles must exist."
   Ensure both "Admin" and "Accountant" roles exist before you assign
   any owner.

7. AUDIT EVERYTHING
   Every mutating endpoint writes a log_activity row. No PII (passwords,
   tokens) is included in audit data.

8. ⚠ PERMISSION GAPS TO FIX BEFORE PRODUCTION
   The following endpoints are currently protected only by IsAuthenticated
   and should be locked to IsSuperAdmin:
     /register/
     /user/list/, /user/detail/, /user/update/, /user/deactivate/
     /role/create/, /role/list/, /role/detail/, /role/update/, /role/delete/
   Without this lock, any logged-in user can list users, escalate their
   own role to Admin, deactivate other users, and manage roles.

9. ⚠ SUPER ADMIN CANNOT UPDATE ORGS THEY DON'T OWN
   /organization/update/ and /organization/deactivate/ filter by
   owner=request.user. Super admin who is not the owner gets 404.
   If super admin should bypass this, the views need:
     Q(owner=request.user) | is_super_admin
   Currently super admin CANNOT update any org's profile.

10. ORG CODE FORMAT
    Auto-generated as ORG-YYMMDD-XXXXX (e.g. ORG-261116-00412).
    Read-only on the serializer.

11. PASSWORD RESET FOR ANY USER
    Super admin cannot reset another user's password from the API.
    /forgot-password/ works only by email match (used by the user
    themselves). If super admin needs to force-reset a user's password,
    that capability doesn't exist — flag for backend.
