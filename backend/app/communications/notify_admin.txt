PAYROLL APP
================================================================================

Admin receives NO notifications from the Payroll app.

Rationale:
  Every payroll action (create run, generate, finalize, edit deductions,
  record payment) is triggered BY the admin. Notifying the admin about
  their own actions is noise.

  The employee-facing events (PAYSLIP_FINALIZED, PAYMENT_RECORDED) are
  one-way — from admin's action to employee's bell. The admin knows
  what they just did and doesn't need a bell entry for it.

  If a future requirement appears to alert the admin about payroll
  exceptions (e.g. generation errors, failed bulk payment rows), that
  would be a new event on the admin side. Not in v1.

================================================================================
ACCOUNTS APP
================================================================================

Admin (org owner) receives NO notifications from the Accounts app.

Rationale:
  - Password change / reset are self-directed security events. The affected
    user is the only recipient. The admin is not in the loop (and should
    not be — passwords are private).
  - User management (super-admin tooling), role management, and organization
    management are admin/super-admin actions the admin performed themselves.
    No self-notification (same rationale as Payroll, Employees, Communications).
  - Login / refresh-token / OTP / profile reads are silent.

  Future: if "admin resets an employee's password" is added, that COULD
  notify the employee (PASSWORD_RESET_BY_ADMIN -> employee). Not in v1 —
  no such endpoint exists yet. Flag if added.

================================================================================
COMMUNICATIONS APP
================================================================================

Admin receives NO notifications from the Communications app.

Rationale:
  Announcements are created BY the admin (org owner). Notifying the admin
  about their own announcement is noise — same rationale as Payroll.

  Chat messages (ProjectChatSendAPIView) are explicitly silent — real-time
  chat relies on polling, not the bell. No notification for chat.

  Notification-bell CRUD (list / mark read / delete) is the bell itself.

  If a future requirement appears (e.g. "another admin published an
  announcement"), that would be a new event. Not in v1 — this is a
  single-owner-per-org system.
