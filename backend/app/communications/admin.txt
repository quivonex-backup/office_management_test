================================================================================
COMMUNICATIONS APP — ADMIN API REFERENCE
================================================================================

Base URL   : /
Method     : All endpoints are POST
Auth       : Bearer token (IsAuthenticated)
Envelope   : { "status": true|false, "message": "...", "data": {...}?, "errors": {...}? }

Organization context:
  - Single-org users: omit organization_id
  - Multi-org users: include organization_id in body

Who uses this document:
  - Organization owner (Admin role)
  - Users whose access role has announcement.manage (default: HR Manager)

Announcements (create / list / update / deactivate) need announcement.manage
(the organization owner has every code). The super admin has NO access to an
organization's announcements (same rule as every other module).
Missing code -> 403 {"status": false, "message": "You do not have permission to perform this action."}

"Admin" for project chat means: the organization owner, or a user with
project.manage (ADMIN on every project), see projects/admin.txt.

Admins are USERS, not EMPLOYEES. They do NOT have a row in the employees
table. They can still post in chat, create announcements, and toggle
chat settings — all through their User identity.

Chat is ALWAYS ENABLED. There is no on/off switch. The only variable is
WHO can post, controlled by each project's posting_permission setting.

RULE FOR THE FRONTEND:
  - Multipart endpoints: ALWAYS use FormData, even with no files.
  - JSON endpoints: use a plain JSON body. Do not send FormData.
  - Attachments use the field name "attachments" (repeat for multiple files).


================================================================================
CHOICE ENUMS — FOR UI DROPDOWNS, FILTERS, AND BADGES
================================================================================

ANNOUNCEMENT PRIORITY (dropdown, badge color):
  NORMAL   — default, grey
  HIGH     — yellow / orange
  URGENT   — red

CHAT POSTING PERMISSION (dropdown, banner copy):
  ADMIN_ONLY      — "Only the admin can post in this chat."
  ADMIN_AND_HEAD  — "Only the admin and project head can post in this chat."
  ALL_MEMBERS     — (default; no banner when caller can post)

CHAT SENDER TYPE (informational; derived, not sent):
  employee_code != null  → Employee sender
  employee_code == null  → Admin sender

Note: There is no "priority" enum for chat messages. Priority only applies
to announcements.


================================================================================
BOOTSTRAP ORDER
================================================================================

  ANNOUNCEMENTS:
    Nothing needed. Admin can create immediately.

  PROJECT CHAT:
    1. Project must exist                   (/projects/create/)
    2. Members must be allocated            (/projects/team-allocation/create/)
    3. (Optional) Head assignment           (/projects/team-allocation/assign-head/)
    4. (Optional) Restrict posting          /communications/project-chat/settings/

  If no ProjectChatSettings row exists, the system creates one with
  posting_permission = "ALL_MEMBERS" on first chat call.

SECTION 2 — PROJECT CHAT (ADMIN)
================================================================================

Chat permissions at a glance:

  ADMIN (org owner or access role with project.manage; not the super admin):
    - Can read any project's chat
    - Can post in any project's chat regardless of posting_permission
    - Can delete any message
    - Can change posting_permission via /project-chat/settings/

  HEAD (active project head):
    - Can read that project's chat
    - Can post if posting_permission is "ADMIN_AND_HEAD" or "ALL_MEMBERS"
    - Can delete any message in that project's chat
    - CANNOT change posting_permission

  MEMBER (any other active team member):
    - Can read that project's chat
    - Can post if posting_permission is "ALL_MEMBERS"
    - Can delete ONLY their own message within 15 minutes

SECTION 3 — DEVICE TOKEN REGISTRATION (FCM)
================================================================================

Every authenticated user must register their FCM (Firebase Cloud Messaging)
device token after login so the backend can send push notifications
(announcements and future notifications).

Register on:
  - First login on a new device
  - Every app launch if the FCM token has changed (FCM tokens rotate
    periodically — usually every 30–90 days, and always on app reinstall
    or data clear)
  - After login on a shared device (transfers ownership of the token to
    the new user)

Only ONE token per device. Registering the same token again just updates
the owner / device_type / is_active — no duplicates.

--------------------------------------------------------------------------------
3.1  POST /communications/device-token/register/
--------------------------------------------------------------------------------
Auth : Any authenticated user
Content-Type : application/json

Request :
{
  "token": "fM3k...long-fcm-token...",
  "device_type": "ANDROID"        // ANDROID | IOS | WEB
}

Response 201 (new token registered):
{
  "status": true,
  "message": "Device token registered successfully.",
  "data": {
    "id": 1,
    "device_type": "ANDROID",
    "is_active": true
  }
}

Response 200 (existing token — owner/type/active updated):
{
  "status": true,
  "message": "Device token updated successfully.",
  "data": {
    "id": 1,
    "device_type": "IOS",
    "is_active": true
  }

Response 400 (missing or blank token):
{
  "status": false,
  "message": "Validation failed.",

  }

================================================================================
CLIENT RESPONSIBILITIES
================================================================================

1. REGISTER AFTER LOGIN
   After every successful login, immediately call this endpoint with the
   FCM token obtained from the device's messaging SDK.

2. RE-REGISTER IF FCM TOKEN CHANGES
   The FCM SDK exposes a token refresh callback. When it fires:
     a) Optionally show nothing to the user
     b) Call /device-token/register/ with the new token
   If the app is closed when the token changes, the next app launch
   should compare the current FCM token to the last-registered one and
   re-register if different.

3. REGISTER ON EVERY APP LAUNCH (SAFEST)
   Re-register on every app launch after auth is confirmed. The backend
   uses update_or_create, so this is cheap and idempotent — 1 HTTP call,
   1 INSERT-or-UPDATE. Do not skip this; FCM tokens can silently rotate.

4. SHARED DEVICE HANDLING
   If a different user logs in on the same device (same FCM token), the
   backend automatically reassigns the token to the new user.
   You do NOT need to "un-register" the previous user's token — the
   reassignment happens on the next register call.

5. NO UN-REGISTER ENDPOINT (CURRENTLY)
   There is no API to deactivate a device token on logout. If you need
   "stop notifications after logout" behavior, either:
     a) Accept that a logged-out device may still receive push until
        another user logs in, OR
     b) Ask the backend team to add a /device-token/deactivate/ endpoint.
   For v1, most apps accept (a) — the token is harmless once the user
   logs out; the next login overwrites it if the device changes hands.

6. DO NOT SEND TOKENS TO UNTRUSTED SERVERS
   The FCM token is a sensitive credential. Only send it to your own
   backend. Never log it in plaintext, never include it in error reports.

SECTION 4 — NOTIFICATIONS (IN-APP + FCM PUSH)
================================================================================

Every notification your account receives — from any app in the system — lands
in a single inbox, delivered by two mechanisms:

  1. **In-app (bell icon)** — stored in the database, visible on the bell
     screen, with read/unread state, pagination, and filtering.
  2. **FCM push** — a device banner appears when a notification is sent.
     Tapping it deep-links into the referenced screen.

Both layers work together. The DB is the source of truth. FCM is the wakeup.

Notifications are auto-created by the backend at specific "trigger points"
in other apps (leave approved, task assigned, reimbursement paid, etc.).
You do NOT create notifications manually — you only consume them.

Per-app event catalog is documented in each app's reference (Leave,
Expenses, Projects, Payroll, etc.). This section documents the notification
**infrastructure** — the 5 endpoints that serve the bell UI and FCM deep-links.

  HIGH     — red / orange (shown with a dot)

Note: notification priority is different from announcement priority
(which has NORMAL | HIGH | URGENT). Notifications only have two levels
because they don't need three visually distinct states in the bell.

================================================================================
FCM PAYLOAD CONTRACT
================================================================================

When the backend sends an FCM push for a notification, the payload looks
like this:

{
  "notification": {
    "title": "Leave approved",
    "body": "Your casual leave from Nov 5-6 has been approved."
  },
  "data": {
    "notification_id": "42",
    "event_code": "LEAVE_APPROVED",
    "reference_type": "leave_application",
    "reference_id": "101",
    "priority": "NORMAL"
  }
}

FLUTTER HANDLERS YOU NEED:

1. onMessage (foreground):
   - App is open, notification arrives
   - OS does NOT show a banner automatically
   - Optional: show in-app toast OR just refresh the bell state
   - Refresh: call /notifications/unread-count/ or /notifications/list/

2. onMessageOpenedApp (background tapped):
   - User taps the banner while app was backgrounded
   - Fires with the `data` payload
   - Navigate: use data['reference_type'] + data['reference_id']

3. getInitialMessage (cold-start):
   - User taps the banner while app was fully closed
   - On next app launch, returns the message
   - Same navigation as #2

RECOMMENDED FLOW:

  FirebaseMessaging.onMessage.listen((message) {
    _refreshUnreadCount();
    // optionally show in-app toast
  });

  FirebaseMessaging.onMessageOpenedApp.listen((message) {
    _navigateToReference(
      message.data['reference_type'],
      message.data['reference_id'],
    );
    _markNotificationRead(message.data['notification_id']);
  });

  FirebaseMessaging.instance.getInitialMessage().then((message) {
    if (message != null) {
      _navigateToReference(
        message.data['reference_type'],
        message.data['reference_id'],
      );
    }
  });

================================================================================
KEY NOTES FOR FRONTEND — NOTIFICATIONS
================================================================================

1. THE BELL IS ALWAYS DRIVEN BY THE DB.
   FCM shows the banner. The DB populates the bell screen.
   They are separate mechanisms. Both are needed.

2. POLLING vs FCM — BOTH SUPPORTED
   - If FCM is active on the device: use onMessage callbacks to trigger
     refreshes. No timer needed.
   - Fallback (FCM not yet registered on this device): poll
     /unread-count/ every 30s while foregrounded.
   The API doesn't know or care which one you use — both work.

3. DEEP-LINKING IS MANDATORY.
   Every notification carries reference_type + reference_id.
   Tapping a notification MUST navigate to the referenced screen.
   Do NOT show a toast-only experience.

4. UNREAD COUNT IS PRECOMPUTED.
   /list/ returns unread_count inline. You usually don't need a separate
   /unread-count/ call after /list/ — use the count from /list/.
   /unread-count/ is for the badge when you're NOT on the bell screen.

5. PAGINATION IS CURSOR-BASED.
   Use before_id = id of the last item on the current page.
   Never use offset/page numbers — they break when new items arrive.

6. PRIORITY IS VISUAL ONLY.
   NORMAL vs HIGH affects badge color/icon in the bell.
   Do NOT change polling behavior based on priority — all notifications
   arrive the same way.

7. DELETE IS HARD DELETE.
   Deleted notifications are gone forever. No undo.
   Mobile apps usually add a "swipe to delete" or "clear all" button.
   For "clear all", call this endpoint with all visible ids — or add a
   /delete-all/ endpoint if the product needs it (currently not present).

8. THE 5 ENDPOINTS ARE SHARED ACROSS ALL APPS.
   Whether a notification is about Leave, Tasks, Reimbursements, or
   Payroll, it appears in the SAME bell list. Filter by event_prefix
   to scope by feature area:
     { "event_prefix": "LEAVE" }         → all leave-related
     { "event_prefix": "TASK" }          → all task-related
     { "event_prefix": "REIMBURSEMENT" } → all expense-related
   No prefix → everything in one unified inbox.

KEY NOTES FOR FRONTEND — ADMIN SIDE
================================================================================

1. ADMIN IS NOT AN EMPLOYEE.
   Admin has NO row in the employees table. Chat sender object shows
   employee_code: null and role_label: "Admin".

2. CHAT IS ALWAYS ON.
   No enable/disable. Only posting_permission varies.

3. THREE POSTING MODES:
   ADMIN_ONLY      — only admin posts
   ADMIN_AND_HEAD  — admin + head post (falls back to admin-only if no head)
   ALL_MEMBERS     — everyone posts (default)

4. HEAD ASSIGNMENT INTERACTS WITH ADMIN_AND_HEAD.
   Head's posting rights appear/disappear dynamically as the head
   allocation is assigned or deactivated. No extra toggle.

5. ANNOUNCEMENTS AUTO-EXPIRE.
   expires_at in the past → hidden from /my/ (employees) but still in
   /list/ (admin).

6. ATTACHMENTS USE S3.
   Full URLs returned in every response. Render them directly.

7. ENVELOPE IS UNIFORM.
   Same { status, message, data } everywhere. Same error shapes.
