================================================================================
PROJECTS APP — EMPLOYEE / PROJECT HEAD API REFERENCE
================================================================================

Base URL   : /
Method     : All endpoints are POST
Auth       : Bearer token (IsAuthenticated)
Envelope   : { "status": true|false, "message": "...", "data": {...}?, "errors": {...}? }

Who uses this document:
  - Any user with an active Employee profile (linked via OneToOneField)
  - The project head for a specific project (gets extra task-management
    endpoints on that project through the ADMIN task endpoints — see NOTE)

CRITICAL IDENTITY RULE:
  The client NEVER sends employee_id or user_id for "who am I".
  The backend derives identity from request.user.employee_profile.
  Sending employee_id has no effect — it's ignored for scoping.


================================================================================
BOOTSTRAP — WHAT EMPLOYEE UI NEEDS
================================================================================

  1. After login, call POST /projects/my-projects/
     → returns all projects I'm on (badge: "Head" or "Member")

  2. Call POST /projects/my-projects-as-head/
     → returns ONLY projects I head
     → store as a set of project IDs to gate task-create buttons on

  3. On project-open, call POST /projects/my-project-detail/
     → shows description, dates, client, head, team, my role

  4. Task list screen, call POST /projects/task/my-tasks/
     → my assigned tasks

  5. Task detail, call POST /projects/task/detail/
     → works for me if I'm the assignee (MEMBER) or the head (HEAD)

  6. Task status, call POST /projects/task/status-update/
     → I can only move TODO↔IN_PROGRESS and IN_PROGRESS→IN_REVIEW

  7. If I'm a project head, all task endpoints work for me on that project
     (task/create, task/list, task/update, task/status-update full matrix,
      task/deactivate) — same endpoints as admin, but scoped to that project.

SECTION 4 — TASK DETAIL (assignee view)
================================================================================

--------------------------------------------------------------------------------
4.1  POST /projects/task/detail/
--------------------------------------------------------------------------------
Same endpoint as the admin one. The backend auto-scopes:
  - HEAD / ADMIN → sees any task in the project
  - MEMBER (assignee) → sees only their own assigned task
  - MEMBER (not assignee) → 403

Request : { "task_id": 500 }
Response 200: { full TaskDetailSerializer }
Response 403: "You do not have access to this task."


================================================================================
SECTION 5 — TASK STATUS UPDATE (assignee view)
================================================================================

--------------------------------------------------------------------------------
5.1  POST /projects/task/status-update/
--------------------------------------------------------------------------------
Same endpoint as the admin one. Assignee is restricted:

Allowed for ME (as assignee):
  TODO        → IN_PROGRESS
  IN_PROGRESS → TODO
  IN_PROGRESS → IN_REVIEW

NOT allowed for me:
  IN_REVIEW   → DONE          (only head/admin)
  IN_REVIEW   → IN_PROGRESS   (only head/admin)
  DONE        → anything      (only head/admin)

Request :
{
  "task_id": 500,
  "status": "IN_REVIEW",
  "actual_hours": "14.00"     // optional
}
Response 200: { full TaskDetailSerializer }

Response 400 (bad transition for my role):
{
  "status": false,
  "message": "Transition from 'IN_PROGRESS' to 'DONE' is not allowed for your role."
}

Response 403 (not my task, not head):
{ "status": false, "message": "You are not allowed to change the status of this task." }


================================================================================
SECTION 6 — AS A PROJECT HEAD
================================================================================

If I am the active head of a project, these ADMIN endpoints become available
to me scoped to THAT project (not other projects):

  POST /projects/task/create/          — create task on my project
  POST /projects/task/list/            — list all tasks on my project
  POST /projects/task/detail/          — see any task on my project
  POST /projects/task/update/          — edit any task on my project
  POST /projects/task/status-update/   — full transition matrix
  POST /projects/task/deactivate/      — soft-delete a task

For OTHER projects where I'm just a member:
  - task/create → 403
  - task/list   → 403
  - task/update → 403
  - task/deactivate → 403
  - task/detail → only my assigned tasks
  - task/status-update → only my assigned tasks, assignee transitions

For OTHER projects where I have NO allocation at all:
  - All task endpoints → 403 "You do not have access to this project."

Frontend pattern:
  On project-open (from /my-project-detail/):
    const iAmHead = data.my_role?.is_project_head === true;
    Show "Create Task" button if iAmHead
    Show "All Tasks" tab if iAmHead
    Show "My Tasks on this project" tab always

================================================================================
KEY NOTES FOR FRONTEND — EMPLOYEE / HEAD SIDE
================================================================================

1. IDENTITY IS DERIVED SERVER-SIDE.
   There is NO employee_id or user_id in any request.
   If the user has no employee_profile → 404 across all endpoints.
   If the employee_profile.is_active=false → 403.

2. HEAD BADGE / TASK-CREATE BUTTON GATING
   Best pattern:
     a) On app load:    call /my-projects-as-head/
     b) Cache set of project ids the user heads
     c) On project-open: gate UI on isHead(projectId)
   The backend still enforces this on the write endpoints — the frontend
   gating is UI polish only.

3. EMPLOYEE CANNOT CREATE TASKS.
   Task-create is HEAD/ADMIN only. Assignee sees tasks assigned to them
   in /my-tasks/ and updates status up to IN_REVIEW.

4. ASSIGNEE STATUS TRANSITIONS ARE NARROW.
   If the frontend blindly shows all four statuses as buttons, three of them
   will 400. Only render:
     - "Start" button when status=TODO
     - "Move to Review" / "Pause" buttons when status=IN_PROGRESS
     - No action buttons when status=IN_REVIEW or DONE for a member
   For a head, all four statuses are valid targets (with the transition
   matrix above).

5. HEAD AND ADMIN SEE THE SAME TASK ENDPOINTS.
   There is no separate "head-create-task" endpoint. The backend's
   get_project_permission helper returns "HEAD" for the head and the
   permission check accepts both "ADMIN" and "HEAD" — so the SAME URLs
   work for both. This keeps URL surface small.

6. "MY PROJECTS" USES ALLOCATION IDS, NOT PROJECT IDS.
   The "id" field in /my-projects/ rows is ProjectTeamAllocation.id.
   To get the project_id, use /my-project-detail/ with the project_id
   from the caller's context (they tapped a specific project).
   If you need project_id in the list, we can add it — say so.

7. NO "MY TEAM" ENDPOINT.
   The full team is already included in /my-project-detail/ response under
   the "team" key. No separate call needed.

8. EMPLOYEE VISIBILITY SCOPE
   - Sees only: active allocations on active projects
   - Sees only: active tasks (is_active=True)
   - Does NOT see: other employees' tasks unless they are the head
   - Does NOT see: deactivated projects, allocations, or tasks
