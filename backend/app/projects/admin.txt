================================================================================
PROJECTS APP — ADMIN API REFERENCE (FULL RESPONSES)
================================================================================

Base URL   : /
Method     : All endpoints are POST
Auth       : Bearer token (IsAuthenticated)
Envelope   : { "status": true|false, "message": "...", "data": {...}?, "errors": {...}? }

Organization context:
  - Single-org users: omit organization_id
  - Multi-org users: include organization_id in body

Who uses this document:
  - Super admin
  - Organization owner (Admin role)
  - Any org member with Admin-level access


================================================================================
BOOTSTRAP ORDER — READ FIRST
================================================================================

  1. Create a client         (separate /clients/ app — prerequisite)
  2. Create a project        (this app)
  3. Allocate employees      (team-allocation/create)
  4. Assign a project head   (team-allocation/assign-head)
  5. (Optional) Create tasks (task/create)

================================================================================
KEY NOTES FOR FRONTEND / UI DESIGNER
================================================================================

1. PROJECT HEAD is per-project, not per-org. One active head at a time.
   - Set via /team-allocation/assign-head/
   - Demote by assigning a different allocation as head
   - No "revoke head" endpoint — replacing is the way to remove
   - project_head appears in /project/detail/ and /project-team/

2. DEACTIVATING THE HEAD'S ALLOCATION leaves the project with NO head.
   UI should prompt: "This was the project head. Assign a new head?"
   Admin still has ADMIN-level task access regardless.

3. TASK STATUS LIFECYCLE
   TODO → IN_PROGRESS → IN_REVIEW → DONE
   - Employee (assignee) moves up to IN_REVIEW
   - Head/Admin moves IN_REVIEW → DONE (the approval gate)
   - Head/Admin can also reopen (DONE → IN_PROGRESS or DONE → TODO)
   UI buttons should be gated by role + current status:
     Member sees: "Start" (TODO), "Move to Review" / "Pause" (IN_PROGRESS)
     Head/Admin sees: full status dropdown with all 4 values

4. TASK ASSIGNMENT requires project allocation.
   Assignee must already be on the project team. Non-members get
   a 400 with "Selected employee is not allocated to this project."

5. project_head object shape (identical everywhere it appears):
   {
     "allocation_id": 30,
     "employee_id": 25,
     "employee_code": "EMP-000025",
     "name": "Rahul Patil",
     "project_role": "Team Lead"
   }
   When null → no head assigned. UI should show "No head assigned"
   with a CTA to assign one.

6. Documents are S3 paths, not URLs.
   "file": "https:/aws.com/abc/projects/documents/project-brief.pdf"
   UI needs to build the full URL via your S3/CDN helper.

7. employee_details shape (used in allocation detail + create + update):
   {
     "id": 25,
     "employee_code": "EMP-000025",
     "name": "Rahul Patil",
     "designation": "Software Engineer",
     "department": "Engineering",
     "employment_status": "ACTIVE",
     "mobile": "9876543210",
     "email": "rahul@example.com"
   }

8. assigned_to_details shape (used in task endpoints):
   {
     "id": 25,
     "employee_code": "EMP-000025",
     "name": "Rahul Patil",
     "designation": "Software Engineer",
     "department": "Engineering"
   }
   (department may be null)

9. created_by_details / updated_by_details / allocated_by_details shape:
   {
     "id": 2,
     "username": "admin_user",
     "email": "admin@acme.com"
   }
   Any of these may be null if the linked user was deleted.

10. DEACTIVATED records are soft-deleted. Nothing is truly deleted.
    - Deactivate project → all list endpoints skip it
    - Deactivate allocation → removed from project-team response
    - Deactivate task → removed from /my-tasks/ for the employee
